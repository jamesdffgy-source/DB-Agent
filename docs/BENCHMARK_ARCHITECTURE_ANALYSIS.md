# DBQuill Benchmark 与架构根因分析

更新时间：2026-08-25 11:50 +08:00

## 结论

低成功率的根因不是单个 Prompt 或一两条 SQL 规则，而是原架构把“模型生成了可执行 SQL”
过早当成任务完成。BIRD 旧完整运行有 58/60 条生产查询可执行，但只有 34/60 结果正确；
这是“可执行性与语义正确性脱节”的直接证据。

当前已完成分层改造，并把独立合同升级到 1.8：

```text
用户问题
  → 有界 Schema / 业务字典 / 值域 Grounding
  → 本地独立 RelationalAlgebraContract 1.8（输出、谓词来源、粒度、排序、路径、集合、聚合、比率、相关键、歧义、tie）
  → 合同完整且 SQLite 节点均可证明：Native Relational Planner + 确定性 SQL
  → 其余形状：模型 QueryIntentContract（输出、粒度、筛选、关联、分组、排序）+ SQL 候选
  → 关系门禁 + 只读/单语句/范围安全校验
  → 类型化语义冲突
  → 合同闭合时：本地投影 / 稳定排序 / 可见元组 DISTINCT / 精确枚举最小编译
  → 最多 4 步单调组合：每步冲突必须变化、SQL 不得循环，终态完整复核
  → 其余冲突：最多 3 个条件化关系计划
  → 每候选范围/关系/只读/语义门禁；唯一证据选择，否则 fail-closed
  → 只读执行
  → 仅对复杂空结果做有界执行反馈复核
```

结果不是“已经根治低准确率”。最新 1.8 已用同一 DeepSeek V4 Flash Prompt/样本/评分契约完成
三次 Spider 固定 100 从零生成：Exact 43/44/43、单发布库执行 76/77/76、严格产品 TSA
61/62/60、上游兼容 TSA 64/61/60。严格 TSA 三轮稳定通过 58、稳定失败 36、波动 6；每轮
15/15/16 个单库通过被多库证伪。三轮固定上游逐题交叉校验均为 100/100，排除了本地比较器漂移。
旧 1.5 的 54 Exact 与 74/75 TSA 是不同 Prompt/生成时间点的历史事实，不能当作单变量回归。
BIRD 最近完整 60 仍是 41/60。
这说明类型化计划已对覆盖到的切片产生实质收益，但一般多阶段查询、复杂筛选、可执行比率、相关标量聚合、
多外键歧义和模型单次生成方差仍是根本差距。

该架构不是形式化 SQL 正确性证明。它把可验证的语义错误从“执行后才发现”前移到“执行前
拒绝或修复”，并提供可审计的中间合同；无法证明的候选仍不能自动视为正确。

## 2026-08-25 三次 1.8 在线生成对架构的进一步推导

三轮 Exact 只有 43/44/43，但单库执行为 76/77/76，说明旧结构匹配继续产生大量等价 SQL 假阴性；
单库再下降到严格 TSA 61/62/60，又证明“一个数据库结果相同”产生 15–16 个数据偶合假阳性。
因此产品发布判断必须以重复生成后的严格多库语义结果为主，Exact、解析覆盖和单库执行只作分层
诊断。58 个稳定严格通过与 36 个稳定严格失败比任何单轮分数更适合指导下一轮架构工作。

稳定残差揭示五个根因：

1. **统一类型化计划覆盖不足。** 本轮目标 IR 只覆盖少量关系路径、聚合阶段和相关性；一般
   GROUP/HAVING、多阶段子查询、集合量词与过滤作用域仍由模型自由 SQL 承担。
2. **输出与聚合粒度未成为全链一等类型。** 输出实体、可见元组集合、事实 bag、`COUNT(*)`、
   `COUNT(DISTINCT entity)` 与 `SUM(measure)` 可被候选互换，直接对应每轮 15–17 个行基数失败和
   17–19 个值/连接/过滤失败。
3. **关系证据缺少业务角色层。** 两题三轮都被关系门禁安全拦截；平行 source/destination 等 FK
   在结构上同等合法时，当前只能澄清。后续应让 schema 注释、业务字典或用户选择形成可审计角色边，
   不能靠模型 JOIN 或 benchmark gold 自动授权。
4. **候选接受不等于独立正确性。** 严格 TSA 有 6 题三轮波动，说明模型方差仍穿过现有合同。
   后续候选选择必须依赖合同覆盖、关系/粒度证据、受控执行特征与明确未知态；三轮 any-pass 只能是
   事后上界，不能成为生产 oracle。
5. **服务长尾是架构缺陷。** 全部调用中位 13.40 秒、P95 193.09 秒、最大 389.42 秒；需要端到端
   deadline、取消/降级和更多本地确定性计划，不能靠无界重试换取偶然正确。

仍需排除 benchmark 口径噪声：未声明次级顺序的单行最值会任意选择并列赢家，而产品稳定 tie 会
选择确定结果；部分 gold 在可见值集合上做 `INTERSECT/EXCEPT`，问句却更自然地要求同一实体同时
满足。它们应单列，不驱动删除稳定 tie、改变实体语义或放宽关系 fail-closed。

## 2026-08-25 多数据库 TSA 对 Relational IR 1.8 的架构推导

单库 85/100 到严格 TSA 74/100 的 11 分回落是关键证据：原架构不仅受旧 Exact 假阴性影响，
也受单库数据偶合假阳性影响。可执行、单库结果相同、旧 AST 接受、合同接受分别只覆盖正确性的
不同侧面，任何一项都不能单独决定候选获胜。固定上游 evaluator 的逐题交叉校验 100/100 排除了
“分数下降只是本地评分器实现错误”这一解释。

| 多库证据 | 暴露的架构缺口 | 1.8 一般性修复 | 仍未完成 |
|---|---|---|---|
| 精确类别被 `%value%` 扩大后仅在部分库多出行 | 操作符强度不属于谓词合同，模型可把等值改成模糊包含 | 样本值唯一精确匹配且问句无模糊词时，本地只把 LIKE 通配收窄为等值；同样可修正唯一枚举大小写 | 一般数值范围、同义值和规范化仍未统一成表达式 AST |
| 带地点/类别限定的 “no relation” 遗漏过滤 | 负相关只保存外层键，没有完整拥有内层谓词 | 限定负关系同时绑定相关路径与唯一引号过滤 | 多条件、OR 与一般相关标量子查询仍回退模型 |
| 单数 most/fewest 在 tie 数据库返回多行或任意一行 | tie 基数和确定性次序分散在 Prompt/SQL 表面 | 单数问法声明 `single_row`；已证明实体键作为稳定次级 ORDER BY，FK 等价键可证明 | 用户真的要任意一个时仍需显式产品语义；一般 top-k 窗口未覆盖 |
| `ALL_VALUES` 隐藏父实体键后重复描述元组 | 内部实体粒度正确不等于用户可见结果集合正确 | 输出丢父键且仅展示描述列时要求 visible-tuple set semantics | 一般投影函数依赖仍需统一图推导 |
| 显式 `'value'` 未进入过滤或落到错误列 | 字面量来源门禁能拒绝无来源值，却不一定正向编译有来源值 | 仅在唯一物理样本列匹配时编译强类型等值；否定/模糊上下文排除 | 无引号实体别名、拼写容错和远程值探针仍需受控设计 |

严格 TSA 的 26 个失败中，行基数 11、值/连接/过滤 9、投影 3，占绝大多数；这支持继续把架构
重心放在“类型化关系计划拥有输出、谓词、粒度和排序”，而不是扩大自由 SQL 候选数量。另一方面，
问句与 gold 的冲突（例如 spending 用 SUM 还是 COUNT、最小输出还是整行、NULL 安全反连接）说明
TSA 也不是产品真值。1.8 只采纳能由问句/schema/样本值/FK/独立反例证明的约束，不读取 case ID
或 gold SQL。

当前 Spider 旧候选重放在执行与产品一致的 12 次稳定 tie、3 次投影、3 次可见元组 `DISTINCT`、
2 次精确枚举和 1 次投影→tie 流水线编译后为接受 95、拒绝 4、澄清 1、错误 0；85 个旧单库执行
通过项全部接受。这里的架构收益不仅是“风险能被
发现并 fail-closed”，还包括“合同已闭合时用本地最小变换修复”，但仍不等于旧候选已经成为新
模型分数。固定原始预测未变，所以 TSA 保持 74/75；21 条本地修复已单独在全部扰动库真实执行，
严格 TSA 改进 3、非并列回归 0、稳定并列策略分歧 7。DeepSeek 最新 1 题探针仍是 HTTP 402、0 个
可评分结果，余额接口鉴权成功但 `is_available=false`。

跨 BIRD 回放给出了必要的反例：直接要求稳定键会拒绝历史 Execution 正确的 `bird-mini-1030`。
根因不是 tie 约束错误，而是“检测与修复”之间仍缺确定性编译层。Local Deterministic Tie Compiler
只对无 CTE/集合操作、明确 `ORDER BY ... LIMIT 1`、表引用唯一且合同键已证明的候选追加次级键，
保持投影、关系、过滤、分组、聚合和主排序不变，再重跑范围/关系/只读/语义门禁。修复后 `1030`
仍为 Execution/严格序列 1/1；BIRD 60 条终态接受 55、拒绝 5，41 个历史正确项新增拒绝 0。既有
投影编译还使 `1179` 的旧失败候选反事实转为 1/1。这说明可靠架构应优先“类型化合同 + 最小本地
编译”，模型候选搜索只处理本地无法闭合的剩余形状。

本轮还确认三个更底层的架构原则。第一，语义证据必须有权威优先级：`Number_products < 3000`
已经唯一落到实体标量列时，不能因为该实体恰有一个入向 FK 就再推断为“关联事实数 < 3000”；否则
同一短语会同时生成 WHERE 与 HAVING，正确单表查询也会被误拒；同理，唯一 schema 输出绑定已经
证明 `Code` 时，较弱投影启发式不得追加 `Code2`。第二，本地编译器必须可组合但必须单调：`0574`
先修复问句输出顺序后才暴露缺失稳定键，因此允许最多 4 步、每步必须产生不同冲突并禁止 SQL 循环，
终态才可执行。第三，本地编译器必须有执行闭环：
静态语义门禁通过不证明结果保持，故单库和多库回放现在都真实执行修复 SQL，并对普通回归非零退出。
稳定次级键可能在主排序并列时故意改变 gold 的任意赢家，因此单独报告确定性策略分歧，而不是混进
普通回归或准确率提升。`DISTINCT` 编译只在完整可见元组合同、简单非聚合 SELECT 中启用；CTE、
集合操作、聚合、窗口、LIMIT/OFFSET 等形状继续 fail-closed。

## 2026-08-25 官方执行重评分对 Relational IR 1.7 的架构推导

真实 SQLite 把“旧 parser 不会解析”“结构不同但结果相同”“当前数据偶合”和“确实改变结果”
第一次分开。固定 100 条的 Exact→执行迁移为：两者通过 52、仅 Exact 2、仅执行 33、两者失败 13；
3 条空结果一致单列为弱证据。执行失败 15 条中，只有一部分是生产缺陷，不能把 gold 全部当产品需求。

| 执行证据 | 架构判断 | 1.7 通用处理 |
|---|---|---|
| `0452` 添加 `round='F'` 后结果改变 | 模型把 schema 常识当成用户筛选，原合同没有谓词来源 | 显式多值问句关闭字符串谓词来源；等值/LIKE/IN 只接受问句、类型化过滤或已声明修饰词 |
| `0700` 按 `phone_number, area_code` 分组得到空集 | `both A and B` 只检查值数量，没有把集合量词绑定到输出实体粒度 | `ALL_VALUES` 保存输出主键、完整多跳 FK 路径和 row grain；事实粒度附加分组拒绝 |
| `0999` 少 `DISTINCT` 产生 15 行而不是 12 个组合 | 行粒度合同只覆盖实体计数，没有覆盖描述性输出组合 | 闭合的 entity label + related description 要求唯一输出 tuple |
| `1033` 的 `with more than 1 room` 可有两种修饰范围 | 自然语言本身不充分，选任一 SQL 都是未经用户授权的猜测 | 布尔作用域作为一等 unknown；模型前澄清，回答后编译强类型作用域并验收候选布尔树 |
| `0937` 产品 `SUM(cost)` 与 gold `COUNT(*)` 选出不同 owner | gold 与“spent most”语义冲突，不能为分数改成计数 | 唯一金额列、实体键和 FK 路径可证明时编译 SUM→实体排名，保留产品 SQL |

当前对 98 条历史 SQL 的本地门禁反事实重放为接受 86、拒绝 11、澄清 1、错误 0；15 个执行
差异中拒绝 7、澄清 1。执行通过但门禁拒绝的 4 条均涉及用户输出顺序或空结果弱证据，说明
denotation 也不能覆盖 UI 输出合同和关系证明；执行失败但门禁接受的 5 条则包含零事实实体、去重
计数、最小必要投影、双向朋友关系和 spending SUM 等 gold 口径弱点。架构必须同时保留问句合同、
schema 证据、安全边界和执行结果，不能把任何一个单独提升为真值。

1.7 的新增节点只在固定 100 中命中谓词来源 2、多值输出粒度 2、金额 SUM 1、描述组合去重 1、
布尔歧义 1；这是有意的高置信覆盖，不靠 case ID 或 gold SQL。下一步不是继续堆正则，而是把这些
节点收敛到统一类型化表达式/粒度图，并用多扰动数据库和独立反例验证。DeepSeek 仍为 HTTP 402，
所以当前不能声称在线生成准确率已经从 54% 提升。

## 2026-08-25 Relational IR 1.5 的当前架构结论

1.5 的关键收益不是把两个 Spider gold 写进规则，而是把 Spider 的标量/聚合粒度残差与 BIRD
的合同误拒放在同一架构上复核。结果证明“计划覆盖不足”和“合同证据过强”同样危险：前者让模型
继续拥有 SQL，后者会用错误的本地确信拒绝正确查询。

| 证据 | 暴露的架构问题 | 1.5 处理 | 仍未证明 |
|---|---|---|---|
| `volvo model` 被模型过滤到相邻 `Make` | 字面量只做词邻近匹配，没有 schema 标签和输出实体路径 | 标签值只绑定到输出实体经唯一最短 FK 可达的唯一文本列；类型化过滤保留真实字面量验证 | 任意多值、OR、模糊实体消歧仍未进入统一计划 |
| “least accelerate 的版本有几个 cylinders”依赖模型自由排序 | IR 有聚合排名，但没有物理标量 arg-min/arg-max | 新增 `ordering_requirements` 与 `RelationalScalarRankingPlan`，本地拥有投影、过滤、FK、排序、limit 和主键次序 | 仅覆盖明确单数、数值列、SQLite 和稳定主键；一般 top-k/窗口仍回退 |
| “template type 最常用于 documents”按模板主键分组会改变类别粒度 | 聚合阶段存在，但 group key 没有绑定“请求的输出值粒度” | 类别使用计划以请求类别列分组、事实表计数、再排名；独立夹具用重复类别证明错误实体粒度会返回不同答案 | 一般多级维度、多个聚合和函数依赖仍未统一表示 |
| Spider 旧 54 Exact 首次回放出现 1 个 count 投影误拒 | 通用输出锁把 `How many entities are ...` 的实体名当标量输出 | count 问句与标量属性问句分型；回放复验后新增拒绝 0/54 | schema-only 回放不能证明旧错误样本已变正确 |
| BIRD 旧 41 Execution Exact 首次回放出现 6 个误拒 | tie 默认值和比率 evidence grounding 缺少证据边界 | 含糊 cardinality 保持未声明；复数/显式 ties 与明确单数分开；公式函数、分子条件不再污染分母 | 比率仍主要是候选合同，不是本地可执行计划 |
| BIRD 第二次回放只拒绝 4 个历史错误候选 | 收紧证据后没有靠“全部不检查”消除误拒，已知错误仍可被合同发现 | 保留时间/总体前缀、唯一 FK evidence 表、事实 FK 分母粒度和关系路径验收 | 旧候选回放不是新模型全量生成，也不衡量未覆盖错误 |

当前最重要的架构变化是：`tie_policy=""` 现在代表“证据不足”，而不是默认全部并列；比率合同也允许
“不声明不确定字段”，不再为了覆盖率生成错误硬约束。Native Planner 只消费完整合同，所以这种
未知态会安全回退模型，而不是部分执行。相反，明确单数标量计划会要求至少一个真实主键作为稳定
次序；Spider `0158` 因额外 PK 次序被旧 Exact 记 0，仍保持产品确定性，不按 gold 删除。

最终源码证据为：Spider 100 旧候选回放旧 Exact 新拒绝 0、可渲染本地计划 9；BIRD 60 旧候选
回放旧 Execution Exact 新拒绝 0、已知错误拒绝 4；独立完整回归 342/342。DeepSeek 定向 Spider
为产品原生结果 2/2、旧 Exact 1/2，BIRD 为 Execution/严格序列 5/5。它们支持本轮两个具体
架构切片与误拒修复，不支持把最新完整 Spider 54/100 或 BIRD 41/60 改成更高全量分数。

下一轮应优先把当前输出/过滤/排序/分组/比率的多个局部编译器收敛成一个带节点依赖和“未知”状态的
统一计划图；随后增加真正可执行的条件比率和一般多阶段子查询。任何新增节点都必须同时通过：
独立 SQLite 反例、旧正确候选零新增拒绝、最终源码在线定向、完整回归和同契约全量重复。

## 2026-08-25 Relational IR 1.4 完整运行后的当前结论

本节是当前架构结论；后面的 1.0–1.3 小节作为演进证据保留，不再代表当前版本。

| 最新实证 | 能证明的架构结论 | 不能外推的结论 |
|---|---|---|
| 同一样本上一完整轮 44/100，本轮 54/100，配对 10 转对/0 转错 | 1.4 没有在这 100 题上制造 Exact 回归，并产生可测净增 | 两轮 Prompt/评分契约不同，不能把全部 +10 都归因于代码 |
| 7 个 Native 计划全部 Exact，单题 0.054–0.366 秒 | 过滤关系排名、最短 FK 路径、`EXCEPT`、`INTERSECT` 和实体去重切片已从模型自由 SQL 前移到确定性计划 | 7% 覆盖不能代表复杂查询或跨方言总体正确率 |

当前架构优先级由这些结果直接推导：

1. 把目前分散的问句编译器收敛为统一类型化语义计划，为输出、过滤、关系路径、实体粒度、
   集合量词、聚合阶段和排序/限制保存证据来源、置信边界与显式 fallback 原因。
2. 获取许可和哈希可验证的 Spider 数据库内容，运行 Test Suite/Execution Accuracy；在此之前
   始终把 parser unsupported、可执行和语义正确分列，禁止用任一项替代另外两项。
3. 对完整轮后最终代码至少运行三次相同样本/模型/Prompt/评分契约，报告逐题稳定组和置信区间；
   单次 54 只作为最近完整点估计。
4. 继续扩大可证明的 Native 计划覆盖，优先一般多阶段聚合、相关标量聚合和复杂筛选；同时给
   模型、候选修复和整个请求链设置共享时间/调用预算，超限可解释降级。
5. 开源发布门槛独立于 benchmark：需要干净环境安装、依赖许可与漏洞清单、支持平台 CI、
   版本化真实夹具、故障注入、升级/回滚与安全边界文档；不得用 342/342 回归替代这些证据。

| 修复层 | 本地投影改写 6 次只 1 次 EX，并造成 3 类回归 | 没有形式语义证明时自动改写会放大检查器误报 | 本地只产生具体冲突证据；模型最多修复一次，仍冲突则不执行 | 尚无跨方言等价性证明和安全的通用 SQL AST 变换 |
| 执行反馈 | 全量 reviewer 的 BIRD 仅净 +1，最大延迟 574.533 秒 | 第二模型复核会改坏正确候选且成本高 | 舍弃全量 reviewer，只对复杂空结果启用；失败时保留已安全执行原候选 | 空结果也可能正确；该 reviewer 只是异常信号，不是默认裁决者 |
| SQL 表达 | Spider 旧 AST 74→65→68→71，当前仍有 26 题被旧解析器拒绝 | 模型会生成等价或近等价但旧评分器不接受的 CTE、CAST、别名、连接/子查询形态 | 原始 SQL 与评分副本隔离，禁止为分数修改生产 SQL | 需真实执行评分；也需在不改变语义时减少无必要 SQL 复杂度 |
| 模型/服务 | Spider 同契约三次 47/47/45 且 11 题翻转；全调用 P95/最大 166.990/403.356 秒 | 生成方差、网络、服务长尾与候选追加调用和代码改动混在一起 | 可比性门槛、逐题稳定性报告、原子检查点、基础设施分母和单提供商总 deadline | BIRD 仍需同契约重复；修正后新 Spider 契约仍需重跑；仍缺整个 mixin/候选会话 deadline 与可用第二模型对照 |

## 消融实验与取舍

1. **全局加长主提示：舍弃。** Spider 两版为 47/100 和 42/100，没有稳定改善。
2. **每条复杂 SQL 都做第二模型 reviewer：舍弃。** BIRD 35/60，相对 34/60 只净 +1，
   但 4 题转对、3 题转错，P95/最大 477.756/574.533 秒。
3. **仅复核复杂空结果：有界保留。** 不增加普通非空查询的第二次调用；reviewer 不可改变
   访问范围或绕过关系门禁。
4. **有界业务字典和值域 grounding：保留。** 定向证据稳定修复 `Discount`、时间戳日期、
   业务代码和 page/url 映射；无关字典片段被相关性排名、16 列和 6000 字符上限截断。
5. **确定性删除多余纯投影：舍弃。** `DISTINCT` 会因删列改变去重键；即使限定非
   `DISTINCT`，BIRD 完整运行 6 次触发也只有 1 次 EX，并造成 coordinates、which-user 和
   legalities-status 三类回归。生产版已彻底撤回该路径。
6. **类型化模型意图合同：保留为审计输入。** BIRD/Spider 覆盖分别 60/60、100/100；不再
   把同一模型自报意图称为独立验证。
7. **本地独立关系代数合同：有界保留，但不再把继续堆单候选规则当作根治。** 1.1 修正两个 Spider 误拒并拦截两个 BIRD 已知错误候选，但 BIRD 总分持平；这证明验收和候选搜索是两个不同问题。下一步用独立关系图约束有界多候选生成/选优，不按样本堆规则。

## 正确性口径

- `exact/execution exact`：自动评分与 gold 匹配。
- `repaired_then_accepted`：一次模型语义修复后通过本地合同并进入只读执行；不等于 gold 命中。
- `rejected_known_conflict`：修复后仍违反高置信合同，未执行；是错误包含改进，在公开基准仍计失败。
- `relation_gate`：多表 SQL 没有 schema 声明关系或用户明确关系，未执行；不为提分猜测 JOIN。
- `production_query_success`：通过安全校验并可执行；不是语义准确率。
- `official_parser_unsupported`：Spider 旧 AST 不支持的预测形态；在没有真实数据时不自动算对，
  也不自动算作产品语义错误。

## 仍需的根本改进

1. 先修正标量属性阈值与关系数量阈值的类型边界，并为候选搜索增加合同完整度门槛；输出、
   目标表、行粒度、筛选、集合、聚合或基数任一关键维度未证明时，不用昂贵多候选冒充裁决。
   然后在 `RelationalAlgebraContract 1.3` / Native Planner 上补过滤、集合/交集、隐式去重、
   outer-entity、相关子查询、top-k tie 和多阶段 GROUP/HAVING。不能退回到只查 SQL 关键字，
   也不能按 benchmark case 编写专用规则或以“能执行”作为唯一准则。
2. 将已完成且与固定上游 100/100 对齐的多扰动数据库 Test Suite 固定为候选重评分门禁，继续将
   数据偶合、空集弱证据、等价 SQL 与真实结构错误分开；生产 SQL 规范化只能做有证明的无语义变化变换。
3. 对同一最终契约至少运行 3 次 BIRD/Spider，报告均值、标准差、稳定通过、成对迁移和延迟长尾；
   当前单次 +3 或 -4 都不能单独证明稳定因果收益。
4. 增加 1000–3000 列 schema 检索压测，以及真实 MySQL/PostgreSQL 方言、类型和值语义验证。
5. 在第二模型凭据可用后做同数据、同 Prompt、同评分契约的盲对照；HTTP 401 只记为凭据/服务
   阻塞，不记为模型质量失败。

## 2026-08-24 下一轮目标关系 IR 实验

本轮把上一节列为缺口的四类结构落实为 `RelationalAlgebraContract 1.3`，但范围仍坚持
“可证明才声明”：

| 目标 IR | 本地证据 | 候选验收 | 低置信边界 |
|---|---|---|---|
| 关系路径 | schema 中唯一最短声明 FK 路径及物理列边 | 实际限定列等值边或同列 `USING` 必须存在 | 平行 FK、多条同长路径不强选 |
| 聚合阶段 | 单数关系 superlative、实体 PK、最近事实表 | 先实体归约/COUNT，再按 ASC/DESC 排名及单行限制；允许绑定正确的相关聚合 | 任意派生指标和多层 HAVING 暂不推断 |
| 比率分母 | 百分比/比例问法、显式列证据、实体 PK/FK、显式日期/分群证据 | 分母保持总体表/实体粒度/基础筛选和倍率；分子条件可更窄 | 无证据的自然语言业务总体不强制 |
| 相关性 | 明确 `without/do not have/do not own/has no`、外层实体和唯一最近 FK 路径 | 绑定正确的 NOT EXISTS、NOT IN 或 LEFT JOIN 空值反连接 | 全局平均与一般相关标量子查询不混入负关系合同 |

实现过程中真实 Spider `0421` 首轮出现三份语义正确候选全部被拒绝。根因不是模型，而是轻量
来源解析把无别名 `FROM visit JOIN museum` 中的 `JOIN` 消费为别名，导致右表没有进入别名表。
修复关键字负向边界后，同题生成：

`museum JOIN visit ON Museum_ID ... GROUP BY museum.Museum_ID, museum.Name ORDER BY COUNT(*) DESC LIMIT 1`

该 SQL 满足目标 IR 和产品语义；Spider 旧 Exact 仍以 `group_having` 计失败，因为 gold 只按
Museum_ID 分组。`Name` 函数依赖主键时附加分组不改变 SQLite 结果，本项目不为适配旧结构评分
删除合法分组列。

Spider `0086` 最终合同同时包含 `AVG(Student.Age)` 与 Student→Has_Pet 的反关联绑定；DeepSeek
返回相关 `NOT EXISTS` 并被本地合同接受。官方旧 AST 对 EXISTS 仍报 unsupported，所以产品语义
验收成功与 benchmark Exact 失败必须分开。BIRD `1493` 最新单点返回同一 `yearmonth` 总体内的
条件计数/总体计数，Execution 与严格序列均 1/1。

BIRD `1037` 则推翻了“它只是选错唯一关系边”的初始假设：数据库实际同时声明
`Player_Attributes.player_api_id → Player.player_api_id` 与
`Player_Attributes.player_fifa_api_id → Player.player_fifa_api_id`，父表两列都唯一；数据中两条边
又存在不一致/悬空差异，显式 evidence 还要求 COUNT(player_fifa_api_id)，但 gold 选择 player_api_id。
因此 1.3 不生成 relation_paths 并让该题继续失败是保守边界，不是合同失效。下一层若要消歧，
需要受访问范围约束的基数/引用完整性证据或用户业务关系声明，不能用 gold 或 case ID 固化选择。

本轮定向运行只用于验证机制：BIRD `1493` 1/1 Execution；BIRD `1037` 0/1；Spider `0421/0086`
均生成产品可执行且通过本地 IR 的 SQL，但旧 Exact 分别因 GROUP 结构与 EXISTS parser 记 0。
这些定向结果不替代完整 BIRD 41/60；后续 Spider 旧生成契约同契约三轮已记录为 47/47/45，
Native Planner 新生成契约首次完整运行已记录为 46/100，但尚缺两次同契约重复。

## 2026-08-25 IR 1.5 失败聚类对 1.6 的架构推导

1.5 完整 Spider 仍为 54/100，但逐题分析不支持“其余 46 题都是生产 SQL 错”。多个差异来自
函数依赖分组列、等价半连接、稳定主键次序、实体键去重和 gold 口径本身；它们不能用于驱动生产改写。
可由问句/schema/独立夹具证明的架构问题集中在三点：

- 输出所有权不完整：物理列按 schema 枚举顺序绑定，导致 `date,id` 和
  `name,result,commander` 被重排。1.6 只在每个列都有唯一问句位置时重排，含糊时不猜。
- 聚合作为输出未入 IR：“教师姓名+教授课程数”被句尾 `how many` 抢占，只剩课程列。
  1.6 用 `output_layout` 表示列+聚合，以实体主键粒度和唯一 FK 路径生成零模型计划。
- 关系数量阈值缺实体粒度：`with at least 2 course results` 既没有编译 GROUP/HAVING，也不能证明关联键。
  1.6 只在输出实体主键和唯一兼容入向 FK 完整时生成阈值合同，多解仍回退。

还有一个与 SQL 架构平行的基准架构缺陷：终止型 HTTP 402 被记作语义失败，且 100 个 future 提前全部提交。
这会同时制造假低分和资源风暴。检查点 schema v2 现在分开可评分分母，首个终止型错误后停止提交并安全续跑。
因此当前“无 1.6 全量分数”是明确的外部依赖状态，不是把中断运行伪装成完整低分。
