这些结果揭示的是通用架构缺口，不是 36 个 case 的字符串补丁清单：

1. 当前目标关系 IR 在本轮 100 题中只覆盖少量关系路径、聚合阶段和相关性，尚未统一表示一般
   GROUP/HAVING、多阶段子查询、集合量词与过滤作用域；大量候选只能在模型 SQL 生成后被动检查。
2. 输出粒度与统计主体没有成为所有查询的一等类型：输出实体、可见元组集合、源事实 bag、
   `COUNT(*)`、`COUNT(DISTINCT entity)` 与 `SUM(measure)` 仍可能被模型互换，直接形成行基数和
   值差异。
3. role-named 平行外键在缺少唯一关系证据时仍会 fail closed；这是安全行为，但产品还缺少可由
   schema 元数据、业务字典或用户澄清闭合的角色关系解析层。
4. 6 个严格 TSA 题三轮波动，说明“一个通过门禁的候选”仍不等于有独立正确性证据。下一层应使用
   类型化合同覆盖、可证明关系/粒度、受控执行特征和明确不确定态做候选选择；三轮 any-pass 的
   事后 oracle 不得作为生产分数。
5. 分钟级 P95/最大延迟要求端到端 deadline、取消与降级，并继续扩大零模型确定性计划覆盖；不能
   通过无界重试换取偶然正确。

另有两类 benchmark 口径不能直接驱动产品降级：未声明次级顺序的单行最值会任意选择并列赢家，
而产品保留稳定 tie；部分 `INTERSECT/EXCEPT` gold 在可见值集合上运算，问句却更自然地要求同一
实体同时满足。它们继续单独记录。不同 Prompt/生成日期下，旧 1.5 候选的 74/75 TSA 与本轮
60–64 TSA 不能被解释为单一代码改动的因果回归。

## 2026-08-25 大 Schema 上下文压力与跨 benchmark 回归

增加特例，而是构造三种同为 3000 列、表宽分布不同的独立 Schema 压力：100 表×30 列、500×6、
1000×3。每个 Schema 只有最后一张 `customer_accounts` 包含目标列，其他表使用重复的
`archive_partition_N` 命名。问句固定为 `Show customer lifetime value for enterprise accounts.`。
旧实现会因 `accounts/account` 形态不一致遗漏 `account_segment`，同时把所有系统化表名的公共 token
当成命中并让无关主键占据列预算。

当前实现使用全库 token 频率降噪、保守单复数归一和 token 边界匹配，并按“可信命中表之间唯一

695 个 SQLite 数据库；评分前核对 dev/tables/固定结果/单库结果哈希、全部 SQLite header、每个
schema 主库 `quick_check` 和完整数据库清单。预测和 gold 都用只读连接、`query_only`、单语句、
超时和结果上限执行。

| 指标 | 结果 | 解释 |
|---|---:|---|
| 旧 Spider Exact Set Match | 54/100 | schema-only 结构指标；大量等价 SQL 被旧 AST 低估 |
| 单数据库执行一致 | 85/100 | 一个发布库上的结果一致；包含空集/数据偶合假阳性 |

严格失败 26 条按结果差异分为：行基数 11、值/连接/过滤 9、投影形状 3、关系门禁 1、仅行顺序
1、生成阶段无查询 1。难度为 easy 23/25、medium 18/25、hard 20/25、extra 13/25。5 条题目
对 `DISTINCT` 处理敏感，因此严格产品口径和上游兼容口径必须并列；不能为了与上游默认值一致而
静默改变生产 SQL 的集合/多重集语义。官方说明使用预测值时不应 `--plug_value`，本轮没有把 gold
值注入预测查询。

TSA 残差同时包含三类事实：真实生产缺陷、当前 1.7 已能拒绝但旧候选未重生成的问题，以及
benchmark 问句/gold/SQL 三者的语义冲突。后者例如问句说“spent most”而 gold 计事实行、问国家
但 gold 返回整行、NULL 敏感 `NOT IN` 与产品更安全的 `NOT EXISTS` 等；这些不能驱动生产逻辑向
gold 降级。可由问句、schema、样本值和声明 FK 独立证明的一般问题升级为 1.8：

- 唯一物理样本列上的显式引号字面量编译精确等值过滤，排除模糊与否定上下文；
- “with no ... in 'value'”等限定负关系同时绑定相关路径和过滤，不再遗漏限定条件；
- 单数/复数 superlative 明确单行与全并列，单行极值要求已证明键的稳定次级排序；
- 精确已知类别不得被候选擅自扩大为 `%value%`；用户明确模糊检索时继续允许 LIKE；
- `ALL_VALUES` 若只输出描述列、隐藏父实体键，则要求可见元组集合去重，覆盖重复关系表达。

当前源码对 100 条旧候选重放时，会执行与产品一致的零模型本地编译：12 条仅追加已证明稳定
tie breaker，3 条使用完整投影编译，3 条只增加已证明可见元组 `DISTINCT`，2 条以唯一 schema
抽样值修正枚举大小写或把未授权通配收窄为等值，1 条按“投影→稳定 tie”两阶段组合。数值短语
已唯一绑定实体标量列时不再重复推断成关系 COUNT；唯一 schema 输出绑定也不再被较弱投影启发式
覆盖。终态为接受 95、拒绝 4、澄清 1、内部错误 0；85 个旧单库执行通过项全部接受。1.8 新节点
分别命中稳定单行 tie breaker 15、问句
superlative 基数 3、引号精确过滤 4、`ALL_VALUES` 可见元组去重 3、限定负关系 1、精确值操作符
门禁 1。本地编译只证明候选可以按当前合同安全修复，不把固定旧候选变成新模型分数；原始预测 SQL
未变，因此固定原始候选 TSA 仍为 74/75。DeepSeek 最新 1 题真实探针仍为 HTTP 402、0 个可评分结果；
鉴权余额接口返回 HTTP 200 但 `is_available=false`，这是外部计费阻塞而非模型准确率。

本地编译不再只靠静态门禁自证。21 条修复后的 SQL 全部重新在单发布库和官方多扰动库执行：

- `spider-dev-0115` 的枚举大小写、`0536` 的通配收窄、`0999` 的可见元组去重均从严格 TSA 失败转为通过；
- 投影、枚举、`DISTINCT` 与组合编译的非并列策略严格 TSA 回归为 0；
- 7 条稳定 tie 编译在存在主排序并列时选择了合同规定的实体键顺序，与没有声明次级顺序的 gold
  任意选择不同。它们单列为 `stable_tie_resolution_divergences`，不冒充修复回归，也不为追分删除
  产品确定性；
- `0574` 的两步组合通过产品合同但仍与排除零事实实体的 gold 不同；`0821` 由唯一 Code 输出绑定
  压过错误要求 Code2 的弱启发式，而 gold 返回问句未请求的百分比。这两项不按分数导向改回；
- 单库执行复核还区分了 2 条执行改进、2 条稳定并列分歧、0 条普通回归。固定上游兼容评分再次

## 2026-08-25 Relational IR 1.5 跨基准回放与最终源码定向

本轮不是按 Spider gold 改 SQL，而是先用 1.4 完整轮和 BIRD 1.1 完整轮保存的候选做零模型
反事实回放，检查新合同是否误拒历史正确查询；随后用独立 SQLite 夹具和最终源码的 DeepSeek
V4 Flash 定向运行验证新增计划。1.5 新增类型化物理标量排序、schema 标签文本过滤、类别值
使用粒度，并修正 count/标量输出、tie 基数和比率分母证据边界。

| 通道 | 回放样本 | 历史正确候选新增拒绝 | 当前本地计划 | 说明 |
|---|---:|---:|---:|---|
| Spider 固定集旧候选 | 100 | 0/54 | 9（原 7 + 新 2） | 9 个均通过渲染和只读校验；schema-only，不是新全量生成分数 |
| BIRD 固定集旧候选 | 60 | 0/41 | 0 | 当前只拒绝 4 个历史错误候选；真实 SQLite 回放不调用模型 |

第一次 Spider 回放曾发现 `How many car models are ...` 被错误绑定为物理 `Model` 投影，造成

新增回归后，第二次回放归零。BIRD 首次回放则发现 6 个历史 Execution Exact 会被错误拒绝：

- `who` 被无证据地强制为 `all_ties`，而复数 `which ... have` 又被宽泛规则误判为单行；
- evidence 里的 `COUNT(`/`SUM(` 被当成同名物理列，拉入无关总体表；
- 分子类别条件（如 `status='A'`、male/female）被错误提升为分母共享过滤；
- `scores between ...` 这类真正的总体范围和事实 FK 分母粒度反而没有被可靠绑定。

修复后，含糊 `who` 保持未声明、复数/显式 ties 保留并列、明确单数保持单行；比率总体只从
问句比较度量、前置总体范围、明确实体、显式时间列和经唯一 FK 连接的 evidence 物理列推导，
公式函数名不参与 schema grounding，分母粒度可由 `COUNT(UserId where ...)` 绑定到事实 FK。

### 三轮后的架构修正

三轮旧契约中新目标 IR 每轮只命中 `spider-dev-0063` 的相关性，关系路径、

## 结论

本报告先建立了可复现的 Spider 1.0 dev 真实模型评测通道，并用固定 100 题对当前
`native_oai_config` 做成对测试。第一阶段经评分适配后，官方 Exact Set Match 从
**46/100 提升到 48/100**，生产只读链保持 **98/100**；主要可归因修复是小中型
schema 不再固定截断到每表前 12 列。

第二阶段继续针对失败样本优化。两版把规则全局加入主提示的实验分别得到 47/100 和
42/100，已因无净收益/明显回归而舍弃；关系门禁顺序审查前的局部候选曾为 48/100，
但其源码契约随后被“关系门禁必须先于语义重试”的安全修正取代，不能当作最终结果。
最终只保留命中时的局部语义重试与 schema 双角色提示，结果为 **47/100**、生产只读链
**98/100**。相对第一阶段 48 分版本为 3 题转对、4 题转错，Exact Match 净减 1；但已确认的多余/遗漏输出列、AND 被裸
`IN` 降级为“任一值”、source/destination 只统计单侧等产品语义缺陷得到修正。不能把
本轮描述为“总分继续提升”。

第三阶段增加 BIRD Mini-Dev 的真实 SQLite 执行评测。账户余额恢复后，优化契约在同一
固定 60 题上已完成 **60/60 非基础设施覆盖**：官方集合式 Execution Accuracy
**34/60（56.7%）**，严格行序 **32/60（53.3%）**，生产只读查询 **58/60（96.7%）**。
难度分层为 simple 16/20、moderate 9/20、challenging 9/20。旧部分基线与新运行只能
对 33 个共同非基础设施题做成对比较：17/33 到 21/33，5 题转对、1 题转错；除
`1339` 有日期位置规则的直接证据外，其他变化不从单次非确定生成归因于代码。

完整运行后又确认并修复两类有真实 schema 抽样证据的缺陷：枚举字面量仅大小写错配，
以及带时间部分的 ISO 时间戳列被纯日期字符串等值比较。`1484/1338` 两题在同一生产
NL2SQL + SQLSecurity 链的在线增量重放中均同时通过官方集合与严格行序评分。据此可计算
固定样本的已知增量结果为 **36/60（60.0%）**，但这是“34 题完整运行 + 2 题新契约定向
重放”的组合证据，不冒充新契约重跑 60/60 的正式分数。

这不是官方排行榜提交，也不是 Execution Accuracy/Test Suite Accuracy。Spider 官方
仓库没有随当前评测代码提供本轮所需的数据库内容，本通道依据官方 schema 构造空
SQLite，因此能验证 schema linking、SQL 结构、生产 SQL 安全执行和官方 AST Exact
Set Match，不能验证条件值或结果行。

## 已确认差距与本轮优化

### 1. Schema 固定截断是可复现缺陷

旧实现只把每表前 12 列交给模型。固定样本中有 4 题的金标必需列全部位于截断位置
之后，4 题优化前全部失败：`0446`、`0451`、`0465`、`0768`。

现实现改为：总列数不超过 384 的 schema 全量进入上下文；更大的 schema 使用全局
384 列预算，优先保留问题直接命中列、PK、FK，同时保留所有表名和明确的省略计数。
第一阶段 `0446`、`0465`、`0768` 通过，`0451` 仍因模型生成了 Spider 旧解析器不支持的
复杂结构而失败；最终版 `0446`、`0465` 通过，`0768` 因模型额外投影 `IsOfficial`
回归。这不推翻字段已经进入上下文的修复证据，但说明形容词“official language”和
布尔列 `IsOfficial` 的输出语义仍可能漂移。

### 2. 局部语义复核修复了三类可确认缺陷

- 投影复核从问句的输出短语中识别明确请求列，排除后续筛选/排序字段；高置信发现
  多余或遗漏列时，把具体字段作为错误反馈给既有自纠错，最终仍由模型重新生成，不
  直接字符串改写 SQL。最终样本 `0179`、`0186`、`0261`、`0363`、`0386`、`0465`
  均返回完整且最小投影；`0768` 是仍存在的形容词/布尔列边界。
- 当问句用 AND/和/与连接两个明确值，而 SQL 只用没有 `HAVING`/双 `EXISTS`/交集的
  裸 `IN` 时触发重试。`0380` 最终使用两个相关 `EXISTS`，`0637` 使用两个 `EXISTS`，
  `0856` 使用 `INTERSECT`；这些结果表达“同时满足”，不再把任一值当成交集。
- schema 中同一事实表若存在 source/destination 两个已声明 FK 指向同一实体，追加
  中立角色提示。`0225` 最终对分角色计数做 `SUM`，同时覆盖出发与到达；没有为了旧
  Spider 解析器强制改写成金标的 OR JOIN。

这套复核只影响只读 SQL 生成重试，不改变关系澄清、SQLSecurity、查询行数上限或写
确认。关系门禁先于语义复核，缺少已声明/显式关系时直接澄清；新增回归保证不会先
重试再改写成单表绕过。两版全局加规则实验退化到 47/100 和 42/100，最终已恢复简洁
主提示，仅在命中高置信偏差时注入具体反馈。

### 3. SQL 复杂度和旧评测语法存在双重差距

原始基线有 34 题、第一阶段有 26 题、最终版有 24 题生成了生产 SQLite 可以执行、但 Spider 1.0 旧解析器
不支持的 SQL，常见形式是 `NOT EXISTS`、CTE、`CAST` 和 `LEFT JOIN`。本轮提示新增
“仅在必要时使用复杂结构、结果列不做无意义别名、记录计数优先 `COUNT(*)`、连接优先
声明外键”。最终旧解析器覆盖率为 74%，但不能把所有等价结构自动改写成金标，
否则会在没有真实数据验证时人为抬高分数。

### 4. 中高难度推理仍是核心短板

最终版未通过题中，主要分类为旧解析器不支持 24 题、聚合/分组 16 题、过滤条件 7 题、
schema linking 4 题、关系门禁 2 题。Hard 为 24%、Extra 为 8%，说明集合操作、嵌套查询、
多阶段聚合和“最多/最少”语义需要专项训练/提示与执行反馈，单纯扩大 schema 上下文
不能解决。

### 5. 产品安全口径与纯 SQL 基准存在有意差异

2 题因为官方 schema 没有声明足够的 FK 路径，被项目的关系门禁转为澄清。Spider 要求
系统直接给 SQL，但 DB-Agent 的长期安全决定是不猜测未声明跨表关系。本轮没有为得分
绕过该门禁；这 2 题在产品口径下是保守行为，在 Spider Exact Match 中仍计为失败。
