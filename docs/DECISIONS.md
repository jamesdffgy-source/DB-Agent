# 架构与产品决策

最后更新：2026-08-26 15:02 +08:00

## ADR-001：完全自研，不接入外部数据库助手框架

- 日期：2026-08-12
- 状态：已接受
- 决定：DB-Agent 不接入、不依赖、不复制外部数据库助手框架。自然语言规划、执行、安全、会话和桌面体验均由本项目实现。
- 原因：产品需要形成自己的能力和优势，避免运行时重量、架构耦合和差异化消失。
- 影响：可以研究公开产品的能力边界，但不能以集成外部框架作为实现路径。

## ADR-002：产品核心是 NL-to-Database Operation

- 日期：2026-08-12
- 状态：已接受
- 决定：自然语言先形成结构化操作计划，再进入元数据、查询、检索、分析或写入执行器。
- 原因：单纯 NL2SQL 无法表达风险、确认、目标、状态和多步骤执行。
- 影响：新增能力应扩展统一操作协议，不能建立绕过该层的隐式入口。

## ADR-003：写操作必须 Human-in-the-loop

- 日期：2026-08-12
- 状态：已接受
- 决定：所有数据或结构写入必须经过安全校验、事务预览和用户显式确认；确认单绑定具体数据库。
- 原因：自然语言和模型输出都存在歧义与误判，数据库写入具有现实破坏性。
- 影响：自动任务中的自然语言写入也只能沿受控确认路径执行，不能为便利绕开安全边界。

## ADR-004：本地优先、轻前端

- 日期：2026-08-12
- 状态：已接受
- 决定：保持 pywebview + aiohttp + 原生前端的便携桌面结构，外部资源尽量本地化。
- 原因：离线可用、部署简单、低依赖和启动可控是产品优势。
- 影响：引入新框架或远程 CDN 前必须证明收益大于体积与运维成本。

## ADR-005：UI 克制并保留文字可读性

- 日期：2026-08-12
- 状态：已接受
- 决定：避免花哨视觉和控件重叠；顶部常用操作保留明确文字，不使用纯图标替代基础含义。
- 原因：数据库工具以信息密度、可理解性和操作安全为优先。

## ADR-006：关键歧义先澄清，不让模型代替用户补齐

- 日期：2026-08-13
- 状态：已接受
- 决定：目标表、修改字段、新值、筛选范围、插入数据或 DDL 定义缺失时，系统必须返回结构化澄清请求，不能直接进入 SQL 生成。连续澄清状态应持久化。
- 原因：模型“合理猜测”对于数据库写入仍可能造成现实损害，变更预览不能替代用户先明确意图。
- 影响：交互可能增加一至数轮，但换取可审计性；定时任务无法交互时，歧义必须作为失败而不是成功处理。

## ADR-007：多步骤组合采用自研只读操作图

- 日期：2026-08-13
- 状态：已接受
- 决定：组合分析先形成显式有向无环图，再经本地校验和拓扑执行。图中只注册查询、检索和综合三类只读能力；写操作不进入操作图，继续沿独立预览与确认链路执行。
- 原因：固定顺序代码无法表达依赖、部分失败和节点状态；让模型直接选择任意工具又会扩大安全边界。确定性图协议可以逐步扩展，同时保持可审计和可测试。
- 影响：当前第一版只支持固定三节点组合模板，不宣称已具备通用自主 Agent；后续动态规划必须继续经过白名单、依赖、环和节点上限校验。

## ADR-008：业务语义必须结构化、持久化并经 schema 校验

- 日期：2026-08-13
- 状态：已接受
- 决定：业务术语不只作为临时提示文本，而是按数据库隔离保存为表别名、字段别名、枚举值、受控指标、业务维度或时间字段；保存和运行时均以真实 schema 为边界。维度和时间语义必须绑定真实字段，时间字段还要通过类型/命名校验；指标只允许固定聚合枚举。
- 原因：临时提示无法跨重启复用，也无法审计来源；自由 SQL 指标会扩大注入和口径漂移风险。结构化目录可以同时服务规划、澄清和 SQL 生成。
- 影响：用户需要显式维护语义定义；schema 变化导致失效的定义会在运行时跳过并暴露为无效项，不能静默映射到其他对象。时间语义只消除字段歧义，不替代时间范围校验。

## ADR-009：离线门禁指标与真实模型准确率必须隔离

- 日期：2026-08-13
- 状态：已接受
- 决定：固定评测分为确定性规划、人工参考 SQL 执行、安全策略和可选真实模型 NL2SQL 四个通道。前三者可以进入离线完成门禁；模型通道必须显式运行，并单独记录模型配置和执行准确率，禁止合并成一个“准确率”。
- 原因：人工标注意图和人工参考 SQL 可以稳定验证自研协议与安全边界，但不能证明模型能从自然语言正确生成 SQL。混合统计会夸大产品能力，也无法进行可复现的模型版本对比。
- 影响：默认门禁无需联网且模型状态为 `not_run`；对外陈述必须明确评测版本、通道和样本量。只有真实模型通道实际完成后，才能报告该固定题集上的模型执行准确率。

## ADR-010：动态操作图只能在本地白名单与固定契约内变化

- 日期：2026-08-13
- 状态：已接受
- 决定：操作图可以按问题特征动态选择关系检查、查询、检索和综合节点，但节点类型、输入输出契约、依赖规则仍由本地代码定义。涉及多表查数时，必须先验证 schema 中已声明外键的连通路径；不允许模型补造表关系。
- 原因：动态选择可以减少无意义模型调用并提升任务可解释性，但让模型自由发明工具、数据结构或 JOIN 关系会使执行不可审计并扩大安全风险。固定契约同时为后续多节点组合提供稳定边界。
- 影响：没有声明 FK 的真实业务关联会被当前版本保守阻断，用户仍可改为直接查询或完善数据库/语义关系；写工具继续禁止进入操作图，所有写入保持预览和显式确认。

## ADR-011：改变读取语义的缺口也必须先澄清

- 日期：2026-08-13
- 状态：已接受
- 决定：读取操作涉及多表但没有可验证关系、派生指标没有受控定义或显式口径、字段聚合没有目标列、时间分析没有唯一字段或具体范围时，必须返回结构化澄清，不把选择交给模型。关系判断由查询门禁与 OperationGraph 共用；当前只接受 schema 外键或用户明确给出的合法等值字段关系。
- 原因：只读操作不会破坏数据，但猜错 JOIN、指标分母或时间窗口会生成可信却错误的业务结论。风险来自语义错误，不只来自写入破坏。
- 影响：部分分析请求会增加一至数轮交互；已有语义指标、明确字段/范围和已声明 FK 的请求保持直达。系统不强制追问不会改变语义的非关键细节，也不宣称已经理解复合公式或业务日历。

## ADR-012：多查询拆分必须确定性、隔离并受预算约束

- 日期：2026-08-13
- 状态：已接受
- 决定：OperationGraph 只在恰好两张目标表且用户明确表达“分别/各自/分开”时拆成独立查询；每个分支只能读取被分配的一张表，拒绝 JOIN、CTE、多表 FROM 和越界表引用。条件分支只能使用本地白名单中的 `has_data`，中间结果和综合上下文必须有固定上限。
- 原因：多查询能表达无需 JOIN 的比较任务，但如果模型可以自由拆节点、选表或决定条件，就会绕过关系门禁并放大数据量、成本和不可审计性。物理只读并不能替代分支语义隔离。
- 影响：明确独立的双表统计无需虚构关联即可执行；包含关联语义的请求仍走关系预检。三表以上、多指标任意拆分、条件嵌套和跨库任务继续保守拒绝或保持现有路径，直到有独立评测和安全契约。

## ADR-013：复合指标先限制为受控单表比率

- 日期：2026-08-13
- 状态：已接受
- 决定：复合指标第一阶段只支持同一张表中的“聚合分子 ÷ 聚合分母”。聚合函数必须来自既有白名单，字段必须存在且数值聚合只接受数值列；结果倍率只允许 1 或 100，分母为零固定返回 NULL。不允许自由 SQL、脚本、任意运算符、跨表公式或指标嵌套。
- 原因：客单价、完成率等常用口径需要结构化表达，但开放自由表达式会扩大 SQL 注入、类型错误、除零和口径漂移风险。有限协议可以被前端选择器、schema 校验、评测与审计完整覆盖。
- 影响：当前可以保存和复用基础比率口径，但组件过滤条件、跨表分子分母、加减乘和嵌套指标仍需独立协议与评测，不能用描述字段或提示词绕过限制。

## ADR-014：语义配置导入必须先预检并原子应用

- 日期：2026-08-13
- 状态：已接受
- 决定：语义配置采用无凭据的版本化 JSON；导入只提供合并模式，必须先以当前 schema 和目录快照完成只读预检，再由用户使用短时一次性令牌确认应用。令牌绑定稳定数据库标识和目录内容版本，批量变更必须在一个事务内提交或回滚。
- 原因：语义定义会直接影响规划、澄清和 SQL 生成。直接导入或逐条落库可能引入失效字段、同名冲突、预检后竞态和半完成状态；携带路径、连接信息或本地 ID 也会降低可移植性并暴露本机信息。
- 影响：同名术语覆盖时保留当前目录 ID，不同名新增，完全一致项跳过；预检后任何目录变化都会使应用失败并要求重新预检。当前协议不是版本发布、替换、审批或回滚系统，这些能力必须另行设计，不能绕过本决定。

## ADR-015：SQL 安全规则只判断真实代码区

- 日期：2026-08-13
- 状态：已接受
- 决定：单语句、危险关键字、危险函数和写操作 WHERE 判断必须先屏蔽字符串、引用标识符、行注释和块注释，只检查真实 SQL 代码区；物理只读连接、事务预览和显式确认继续作为独立防线。
- 原因：对原始文本直接正则会让注释中的 WHERE 伪造筛选条件，也会把字符串中的分号或 DROP 误判为多语句/危险写入。安全误放行和误拒绝都不可接受。
- 影响：当前轻量词法层覆盖常见引号和注释，但不是完整方言解析器；新增远程方言或特殊引用语法时必须增加固定对抗样本，不能据此宣称已形式化证明 SQL 安全。

## ADR-016：业务日历先作为必填口径，不由模型猜测

- 日期：2026-08-13
- 状态：已接受
- 决定：财年、财季、工作日、交易日或营业日分析在缺少业务日历口径时返回结构化澄清；用户提供明确口径后才可继续。当前不把提示文本等同于结构化日历计算引擎。
- 原因：同一日期在不同企业、市场和地区可能属于不同财年或工作日。只读查询猜错日历同样会生成可信但错误的业务结论。
- 影响：财年起点、节假日表、时区和例外规则仍需后续独立协议。明确口径只解除歧义门禁，不代表系统已完成可复用日历治理。

## ADR-017：指标过滤只接受同表结构化 AND 条件

- 日期：2026-08-14
- 状态：已接受
- 决定：普通指标以及比率指标的分子、分母可以保存过滤条件，但每组最多 4 条，只允许同一目标表的真实字段，并仅按 AND 组合。操作符固定为等于、不等于、范围比较、IN/NOT IN、为空/不为空；IN/NOT IN 最多 20 个字面量值。字段、值类型和范围比较能力必须在保存时通过 schema 校验，不接受自由 SQL、OR、子查询、跨表条件或可执行表达式。
- 原因：已付款成交额、有效订单数、完成率等常用指标需要稳定过滤口径；把 WHERE 文本交给用户或模型保存会重新引入注入、口径漂移和不可审计问题。有限条件协议可以由前端控件、后端校验、持久化、导入导出和固定评测共同覆盖。
- 影响：SemanticCatalog 升级为 2.2，可移植配置升级为 schema v2 并继续兼容导入 v1。过滤值只作为字面量提示进入 NL2SQL，最终 SQL 仍需模型生成并接受现有只读安全校验；在真实模型评测完成前，不能声称过滤指标 SQL 准确率已验证。OR、跨表过滤、相对时间和嵌套条件需要单独协议与评测，不能通过描述字段绕过。

## ADR-018：业务日历必须绑定时间字段并采用有限结构化协议

- 日期：2026-08-14
- 状态：已接受
- 决定：把业务日历作为 `SemanticCatalog 2.3` 的第八类定义。每个日历必须绑定当前 schema 的真实时间字段，只接受财年起点、UTC/IANA 风格时区标识、ISO 周起始与固定非工作日；节假日例外只能通过显式绑定的真实表及日期/名称/工作日覆盖字段表达。财年或工作日请求只有在时间字段匹配时才能自动使用日历；不得用同表日历替代用户明确引用的另一时间字段，不接受自由 SQL、脚本或模型自造节假日。
- 原因：日历口径不仅因企业而异，同一业务表的创建时间、结算时间和更新时间也可能服从不同日历。把日历仅保存成描述文本无法验证目标字段、例外来源和类型，按表泛化又会产生可信但错误的时间归属。
- 影响：可移植配置升级为 schema v3 并继续兼容导入 v1/v2；语义工作台新增结构化日历编辑区。当前实现只校验并传递日历口径，最终日期 SQL 仍由模型生成；时区标识只做语法校验，便携运行时没有 `tzdata`，也没有确定性财年/节假日展开与跨时区换日引擎。在相应实现和真实模型评测完成前，不得声称业务日历查询已全面准确。

## ADR-019：确定性日历执行先限定为 SQLite 声明型 DATE 聚合

- 日期：2026-08-14
- 状态：已接受
- 决定：确定性业务日历第一版只处理 SQLite、schema 声明型 `DATE` 字段、单表、明确财年或明确起止日期的工作日请求，以及 COUNT/受控普通指标。财年必须显式选择按起始年或结束年标注；旧配置缺少该字段时保留 `legacy_default` 标记并回退模型。财年使用 `[start, end)` 半开区间，显式工作日范围包含首尾；例外表中非零覆盖表示工作日并优先于同日非工作记录。任何分组、排序、明细、比率、未知附加条件、非 DATE 字段或远程方言都不得通过删减语义进入该执行器。
- 原因：DATE 值不需要解决时间戳存储时区与换日问题，可以由 SQLite 内建日期函数稳定验证；而把轻量 SQL 改写推广到时间戳、复杂查询或其他方言，会产生难以察觉的边界偏移和条件丢失。严格完整形状匹配与保守回退比部分“自动优化”更可审计。
- 影响：新增 `CalendarFilterPlan 1.0`、`native_calendar` 执行器和独立固定评测通道，日期边界、谓词、例外规则及最终 SQL随回答返回。SemanticCatalog 升级为 2.4，配置升级为 schema v4 并兼容导入 v1-v3。当前通过率只证明列明的 SQLite DATE 用例；时间戳存储基准、跨时区、财季、分组、比率、跨表及 MySQL/PostgreSQL 必须另立协议和评测。

## ADR-020：时间戳确定性换日必须声明存储基准，IANA 名称不作为执行规则

- 日期：2026-08-14
- 状态：已接受
- 决定：SQLite 时间戳进入确定性日历执行前，业务日历必须显式声明 `local_datetime` 或 `utc_datetime`。前者表示 DATETIME/TIMESTAMP 已按业务本地墙上时间存储且不执行时区换算；后者表示值是 UTC 时间戳，并必须提供 -840 到 840 的整数固定业务偏移。声明型 DATE 可由 schema 安全推断为 `declared_date`；TEXT、未声明/旧时间戳、类型不匹配均回退。IANA 风格时区继续作为业务标识和模型上下文，不得在缺少时区数据运行时与版本验证时被解释为 DST 动态换算规则。明确的第 1–4 财季按财年起点每三个月生成半开边界；不能形成精确日界时回退。
- 原因：同一 UTC 瞬间在不同业务时区可能归属不同日期，而 SQLite 声明类型本身不能说明值是 UTC 瞬间还是本地墙上时间。直接套用 `date(column)` 或从 IANA 名称猜偏移会在换日和夏令时边界产生隐蔽错误；固定、显式、可审计的分钟偏移可以在不引入未验证时区数据库的情况下覆盖稳定业务口径。
- 影响：SemanticCatalog 升级为 2.5、CalendarFilterPlan 升级为 1.1、可移植配置升级为 schema v5；导入继续兼容 v1-v4。当前“时间戳确定性支持”只指 SQLite 声明型 DATETIME/TIMESTAMP 与显式固定口径，不能表述为 IANA/DST、TEXT 时间串或远程数据库已支持。后续如引入动态时区转换，必须固定 tzdata 版本、增加 DST 对抗样本并另立决策。

## ADR-021：维度层级只表达同表路径，趋势粒度必须显式或受控默认

- 日期：2026-08-14
- 状态：已接受
- 决定：业务维度可选声明名称和 1–8 级顺序，但同一层级名只能绑定一张表且每个级次唯一；层级仅作为有序语义路径进入解析和提示，不能据此自动创造跨表 JOIN。时间字段可选声明日、周、月、季度或年的趋势默认粒度；用户显式粒度优先，趋势请求没有显式粒度且绑定字段也没有唯一默认值时必须返回 `time_grain` 澄清。普通时间过滤不因此增加追问。
- 原因：地域、组织、商品等层级可以改善分组与钻取语义，但跨表层级会隐含未经验证的关系；趋势聚合缺少粒度会生成形状完全不同且看似合理的结果。受控同表路径和有限枚举默认值可以被 schema、导入、UI、多轮澄清与固定评测共同验证。
- 影响：SemanticCatalog 升级为 2.6，可移植配置升级为 schema v6 并兼容导入 v1-v5。当前实现不等于确定性钻取或通用时间分组编译器；最终 SQL 仍需模型生成并通过既有只读安全边界，真实模型通道未运行前不得声称层级/默认粒度 SQL 准确率已验证。

## ADR-022：确定性维度执行只接受完整可识别的 SQLite 单表聚合

- 日期：2026-08-14
- 状态：已接受
- 决定：维度确定性执行第一版只处理 SQLite、单张真实表、一个显式业务维度或一个已验证的同表层级路径，以及 COUNT 或一个受控普通指标。明确“从 A 下钻到 B”时 B 必须与 A 同表、同层级名且更深；“下钻一级”必须存在唯一连续下一级；其他未明确目标的下钻先返回 `dimension_level` 澄清。指标过滤和枚举条件只能来自已校验结构化语义。任何自由条件、比率、时间/日历混合、字段别名、并列多指标、跨表、远程方言或无法完整消去的自然语言片段都不进入该执行器，完整回退既有 NL2SQL。
- 原因：简单维度分组和同表下钻具有稳定、可验证的 SQL 形状，可以减少模型依赖；但部分理解后静默丢弃过滤、跨表关系或额外指标会产生可信但错误的统计。严格完整形状匹配、物理只读执行和可审计计划比追求更高命中率更重要。
- 影响：新增 `DimensionAggregatePlan 1.0`、`native_dimension` 执行器、`dimension_plan` 回答协议和固定维度评测通道。当前通过率只证明列明的 SQLite 单表用例，不代表通用 OLAP、跨表钻取、自由筛选、多指标或真实模型生成 SQL 已完成；扩展边界前必须新增相应协议、对抗样本与回退测试。

## ADR-023：确定性趋势执行只接受受控时间字段与完整单表形状

- 日期：2026-08-14
- 状态：已接受
- 决定：时间趋势确定性执行第一版只处理 SQLite、单张真实表、一个经 schema 校验的时间字段、日/周/月/季度/年粒度，以及 COUNT 或一个受控普通指标。用户显式粒度优先，否则趋势请求可使用该时间字段的唯一语义默认粒度；周桶固定以 ISO 周一为起点。可选日期范围只接受完整 `YYYY-MM-DD` 起止值并包含首尾。声明型 DATE 可直接分桶；DATETIME/TIMESTAMP 必须由同字段唯一业务日历显式声明 `local_datetime` 或 `utc_datetime`，UTC 继续只使用已登记固定分钟偏移。任何相对时间、自由条件、比率、业务日历/财年趋势混合、多个时间字段或并列指标、跨表、远程方言及无法完整消去的自然语言片段都不进入该执行器。
- 原因：自然时间粒度的单表分桶具有稳定可验证的 SQL 形状，能减少常见趋势请求对模型的依赖；但周起点、时间戳换日、相对“最近”边界和复合条件都可能显著改变统计结果。严格时间字段、存储口径、粒度来源和完整形状匹配可以避免生成可信但错误的趋势。
- 影响：新增 `TrendAggregatePlan 1.0`、`native_trend` 执行器、`trend_plan` 回答协议和固定趋势评测通道。当前通过率只证明列明的 SQLite 单表自然时间分桶、精确日期范围、受控指标和固定偏移用例；不代表相对时间、财年分桶、IANA/DST、跨表、多指标、远程方言或真实模型 SQL 已完成验证。扩展边界前必须新增结构化协议、边界样本与严格回退测试。

## ADR-024：IANA/DST 动态换日必须固定数据版本并由 SQLite 受控函数执行

- 日期：2026-08-14
- 状态：已接受
- 决定：便携运行时固定分发 `tzdata 2026.3`（IANA `2026c`）。只有 SQLite 声明型 DATETIME/TIMESTAMP、显式 `storage_basis=utc_datetime`、`timezone_conversion=iana_tzdata`、真实存在的区域时区以及与运行时一致的数据版本可以进入动态换日。UTC 源值允许 `Z/+00:00` 或无后缀 UTC 文本，带非零偏移、非法格式或非法日期返回 NULL 并从确定性趋势中过滤。只读连接注册确定性三参数 `dbagent_iana_date(value, zone, version_token)`，编译后的 SQL 和回答计划必须同时携带时区、tzdata/IANA 版本；缺包、版本漂移或未知区域在配置阶段拒绝。原固定偏移协议保持兼容，不从名称自动推断 DST。
- 原因：Windows 便携 Python 没有系统 `TZPATH`；仅接受 IANA 风格字符串会产生“配置看似正确、实际无法换算”的假支持。把版本固定在应用内，并把版本令牌绑定到 SQL 执行，可以让冬夏偏移和历史规则在测试、导入和审计中复现；同时避免依赖主机时区库静默变化。
- 影响：SemanticCatalog 升级为 2.7、CalendarFilterPlan 升级为 1.2、TrendAggregatePlan 升级为 1.1，可移植配置升级为 schema v7 并兼容导入 v1-v7。语义工作台新增固定偏移/IANA 动态换日选择，审计条显示区域和 IANA 版本；固定评测 v15 加入纽约冬夏跨日与非法 UTC 源值样本。该能力只证明列明的 SQLite 路径，不代表 TEXT 时间串、系统/远程数据库时区函数、未来规则自动更新、所有历史区域或真实模型 SQL 已验证。

## ADR-025：显式独立查询扩展到最多六个单表分支

- 日期：2026-08-14
- 状态：已接受；取代 ADR-012 中“恰好两张目标表”的数量限制，其余隔离和预算原则不变。
- 决定：只有用户明确表达“分别/各自/逐个/分开”、至少命中两张目标表且没有关联/JOIN 语义时，OperationGraph 才按目标表生成独立 query。分支数量上限为 6；每个分支必须绑定一张唯一表、没有关系推断或其他上游依赖、按顺序完整覆盖目标表，并直接纳入综合节点依赖。7 个以上分支在任何查询或检索工具运行前拒绝。每支继续拒绝 JOIN、CTE、多表 FROM 和越界表引用；部分分支失败只保留成功数据集并标记图为 partial。
- 原因：执行器和 `datasets` 协议已天然支持任意数量结果，原“两表”限制只是规划器硬编码。将上限固定为 6 可覆盖常见独立比较，同时让现有最多 8 节点预算仍容纳六查询、一个条件检索和一个综合节点，不扩大为模型自由拆图。
- 影响：三至六张表的明确独立统计不再需要虚构关系，也不会绕过单表范围校验；关系语义仍走 FK/显式等值关系门禁。同表多指标语义拆分、7 张以上分支、嵌套条件、跨库任务和隐式关系仍不支持。

## ADR-026：同表并列普通指标使用一次性条件聚合

- 日期：2026-08-14
- 状态：已接受。
- 决定：SQLite 上同一张表命中 2–6 个经 schema 校验的普通指标、没有比率/维度/时间/日历/字段别名等其他语义且自然语言剩余片段可完整消去时，使用 `MultiMetricAggregatePlan 1.0` 编译为一条只读 SELECT。每个指标的结构化过滤只进入该指标的 CASE 条件聚合；最多一个同表枚举作为全局 WHERE。列顺序按用户提及顺序。两个以上枚举、自由算术、7 个以上指标、跨表、远程方言或无法完整识别的形状整体回退既有链路，不执行可识别子集。
- 原因：同表指标拆成多次查询会增加模型/数据库调用，并可能跨越不同数据快照；一条受控聚合 SQL 能原子地返回多个结果。指标过滤若合并进全局 WHERE 会错误改变其他指标，因此必须以条件聚合隔离；全局筛选则需要与指标内过滤明确区分。
- 影响：普通指标并列查询可不经模型直接执行，并通过 `metric_plan` 审计表、指标、过滤和 SQL；用户说“分别”但只涉及同表多个普通指标时归一为一次只读查询，不创建 OperationGraph。当前不扩展到比率、通用算术、维度/趋势多指标、多个枚举、跨表或 MySQL/PostgreSQL。

## ADR-027：维度多指标沿用同表条件聚合并保持单指标兼容

- 日期：2026-08-14
- 状态：已接受；取代 ADR-022 中“一个受控普通指标”的数量限制，其余完整形状和回退边界不变。
- 决定：SQLite 单表的一个显式业务维度或已验证同表下钻路径可携带 1–6 个普通受控指标。多指标时，每个指标自带过滤只进入该指标的 CASE 条件聚合，最多一个同表枚举作为全局 WHERE；列顺序按用户提及顺序。单指标继续把指标过滤放入 WHERE，以保持既有分组集合语义。`DimensionAggregatePlan` 升级为 1.1，新增完整 `measures` 和 `global_filters`，保留首个 `measure` 字段兼容已有消费者。
- 原因：维度分组与无维度并列指标共享相同的过滤污染风险，但直接把单指标也改成条件聚合会让原本不出现的零值分组重新出现，构成行为变更。区分单/多指标编译方式可以在扩展能力的同时维持已经评测过的旧语义。
- 影响：同表分组和同表下钻可一次返回多个普通指标，桌面审计展示全部指标；自由条件、比率、多个全局枚举、7 个以上指标、跨表维度、时间趋势多指标和远程方言仍整体回退。

## ADR-028：趋势多指标隔离指标过滤并共享受控时间谓词

- 日期：2026-08-14
- 状态：已接受；取代 ADR-023 中“一个受控普通指标”的数量限制，其余受控时间字段、粒度、换日与完整回退边界不变。
- 决定：SQLite 单表的一个受控时间字段和日/周/月/季度/年粒度可携带 1–6 个普通受控指标。多指标时，每个指标自带过滤只进入该指标的 CASE 条件聚合；日期有效性、精确起止范围、固定偏移或固定版本 IANA/DST 换日以及最多一个同表枚举作为所有指标共享的 WHERE。列顺序按用户提及顺序。单指标继续把指标过滤放入 WHERE，以保持既有时间桶集合。`TrendAggregatePlan` 升级为 1.2，新增完整 `measures` 和 `global_filters`，保留首个 `measure` 字段兼容已有消费者。
- 原因：时间分桶与维度分组有相同的指标过滤污染风险，但日期/换日谓词决定记录属于哪个时间桶，不能下沉到单个指标。直接把单指标过滤改成条件聚合还会新增原先不出现的零值时间桶，因此需明确区分全局时间谓词、全局业务过滤和指标局部过滤。
- 影响：同表时间趋势可一次返回多个普通指标，且继续复用已经验证的日期范围与 IANA 版本绑定；桌面审计展示全部指标。自由条件、比率、两个以上全局枚举、7 个以上指标、多个时间字段、相对时间、业务日历/财年趋势组合、跨表和远程方言仍整体回退。

## ADR-029：维度固定过滤属于维度口径而不是自由自然语言条件

- 日期：2026-08-14
- 状态：已接受；扩展 ADR-021/ADR-022，保持同表层级与完整形状回退原则。
- 决定：每个业务维度可配置最多 4 条同表结构化过滤，字段、操作符、值类型、IN 上限与指标过滤使用同一白名单，只允许 AND。确定性分组或下钻时，所选路径中全部维度的固定过滤按完整结构去重，唯一条件合计最多 4 条，并作为所有指标共享的 WHERE；超过上限整体回退。指标自带过滤和枚举值仍分别遵守既有局部 CASE/全局 WHERE 规则。`SemanticCatalog` 升级为 2.8、`DimensionAggregatePlan` 升级为 1.2；计划单独返回 `dimension_filters`。可移植配置升级为 schema v8，导入兼容 v1–v8，旧版仅层级对象的 SQLite 载荷继续读取。
- 原因：枚举值表达用户在问题中显式提到的成员，而维度固定过滤表达“该维度本身只统计哪些记录”的团队口径，两者生命周期和审计含义不同。复用已有结构化过滤协议可以避免自由 SQL、OR 和跨表条件进入语义目录；路径去重可防止上下级重复定义同一口径时产生冗余谓词。
- 影响：可以定义“活跃客户区域”“在售商品分类”等受控维度并在分组/下钻中稳定复用；语义工作台、持久化、导入导出、提示上下文和回答审计都携带该口径。该能力不是临时自然语言筛选器，不支持 OR、跨表过滤、超过 4 条路径条件或未配置的自由条件。

## ADR-030：相对趋势必须固化参考日，业务日历窗口复用唯一结构化口径

- 日期：2026-08-14
- 状态：已接受；扩展 ADR-023/ADR-028，不改变单表、受控时间字段、物理只读和完整形状回退原则。
- 决定：`TrendAggregatePlan 1.3` 只把“最近/近/过去 N 天或 N 周”编译为包含参考日在内的连续日窗口，N 折算后最多 3660 天。用户可用“截至 YYYY-MM-DD”指定参考日；否则在请求时读取运行时本地日期并立即固化到计划，SQL 不使用 `CURRENT_DATE` 等随执行时刻漂移的表达式。财年、财季和工作日趋势必须由与目标时间字段唯一绑定的结构化业务日历生成范围与例外谓词；财年/财季沿用半开边界，按周分桶使用日历 `week_start`。显式日期范围、相对窗口和日历窗口发生冲突时整体回退。
- 原因：相对时间若不记录参考日，同一句问题在重放或延迟执行时会改变结果；把月、季度、年简单折算为固定天数会在月末和闰年制造隐蔽偏差。财年和工作日已有经过版本化验证的结构化边界，趋势执行器应复用而不是复制或让模型重造规则。
- 影响：相对日/周和财年/财季/工作日趋势可以在 SQLite 单表确定性执行，并在 `trend_plan`/桌面审计中暴露窗口来源、具体边界、参考日、日历模式与周起始。滚动月/季度/年、超过上限、多个或冲突窗口、相对与财年混合、财年专用分桶、自由条件、跨表和远程方言仍不属于该协议；真实模型通道未运行前不能外推模型准确率。

## ADR-031：IANA 规则使用可并存的项目归档发布，激活只改变新定义默认值

- 日期：2026-08-17
- 状态：已接受；扩展 ADR-024，并取代其中“运行时直接依赖便携 Python 已安装 tzdata 包内容”的实现方式。版本令牌、SQLite 范围和保守回退原则保持不变。
- 决定：每个 IANA 发布以项目自带的确定性 ZIP 保存 `release.json` 与 TZif 条目，由清单绑定发布 ID、tzdata/IANA 版本、SHA-256、区域数和 4–64 个转换探针。运行时只从已登记归档加载规则，不读取主机 `TZPATH` 或当前已安装包内容。多个发布可并存；业务日历继续绑定保存时的版本，切换活动发布只改变新定义默认版本。候选必须经本地 `prepare` 暂存并验证元数据、哈希、TZif、区域数和探针后才能登记；同一版本号不同内容禁止覆盖。`activate` 和 `rollback` 必须先验证目标并原子更新活动/回滚指针，失败恢复原清单。
- 原因：只校验“安装包版本号等于常量”仍无法证明实际 TZif 内容未漂移，也无法在升级后重放旧业务口径；直接覆盖单一包还会让既有日历失效。内容哈希、并存归档和候选探针使升级前验证、旧查询复现及显式回滚成为同一契约的一部分。
- 影响：新增 `timezone_release_contract.py`、`timezone_releases/` 和离线管理脚本；当前完整发布为 `tzdata-2026.3-iana-2026c`，598 区域并通过纽约/悉尼季节边界、伦敦历史、阿皮亚日期线、加德满都非整点偏移和卡萨布兰卡规则 8 个探针。门禁把 ZIP 纳入源码指纹，并在状态 schema v3 记录发布哈希与探针。桌面只展示活动版本且编辑时保留旧定义版本；发布切换后必须完整重启常驻后端。该决定不授权联网下载或自动激活，也不代表下一真实上游版本、全部历史区域、性能或远程数据库方言已经验证。

## ADR-032：真实模型评测与离线门禁隔离，基线以脱敏追加历史记录

- 日期：2026-08-17
- 状态：已接受；扩展 ADR-010，不改变“离线指标不得冒充模型准确率”的原则。
- 决定：真实模型通道只有显式运行 `--with-model` 才访问当前配置，项目离线门禁永不自动调用外部模型。每次可登记运行必须绑定固定评测版本、数据集 SHA-256、NL2SQL 提示词指纹、模型/配置/API 模式、接口地址的不可逆短哈希、逐题 SQL/错误/结果判定和延迟；不得保存 API key、原接口地址或用户数据库内容。历史只能追加新运行，失败同样保留。相同题集可比较提示词或模型变化，但报告必须标出变化、改进、回归和延迟差异。
- 原因：只把最近一次模型分数写进会被离线报告覆盖的文件，无法复现版本差异，也容易选择性忽略失败；把密钥或完整接口写入报告又会制造凭据泄露。追加式、脱敏、哈希绑定的记录既能审计优化影响，也不把外部调用引入默认门禁。
- 影响：固定评测 v23 保持离线 134 项，并把独立真实模型题扩展到 12 项；新增 `model_baseline_contract.py`、`MODEL_BASELINES.json` 和 `run_model_baseline.cmd`。NL2SQL 初始 v22 基线 9/12 暴露额外投影，提示增加最小必要列后 v22 为 11/12；统一“客户是谁”的期望后 v23 首次为 12/12。该 12/12 只代表指定模型在 12 个合成 SQLite 问题上的一次运行，不是稳定性、真实业务、远程方言、大 Schema 或普遍模型准确率证明。

## ADR-033：操作审计使用脱敏追加事件链，数据变更在审计异常时 fail-closed

- 日期：2026-08-17
- 状态：已接受；新增生产安全边界，不取代写预览、一次性确认单、数据库绑定、执行前复检或事务回滚。
- 决定：自然语言终态、用户写确认/执行及语义目录变更统一写入独立本地 SQLite 审计账本。账本详情采用显式字段白名单，禁止保存原始问题、SQL、结果行、数据库路径、连接串和凭据；问题、SQL、目标、语义术语及确认单只保存不可逆指纹。事件只通过模块追加，按连续序号、前序哈希和当前 SHA-256 哈希链接，不提供历史更新/删除 API。查询和导出必须返回或验证完整性状态。用户写确认与语义变更在调用实际执行器前必须先验证已有链并成功登记批准/拒绝事件；账本不可用或链异常时 fail-closed。自然语言只读操作的结果审计采用 fail-open，不能因日志故障改变物理只读查询结果。
- 原因：内存任务状态、会话消息、调度 Markdown 和写确认结果分别存在，无法形成统一的操作事实；保存原文又会让审计库复制业务数据、SQL 和凭据。变更前的强制意图事件可以保证“明知审计不可用仍继续写入”的路径被阻断，前向链可发现普通历史修改、删除或断链，字段白名单把泄露面限制在必要元数据。
- 影响：新增 `db_audit_store.py`、三组受鉴权审计 API 和桌面“审计记录”工作台；自然语言、写确认/执行、语义新增/删除/导入拥有统一分类、动作、结果、风险和关联引用。用户数据库与审计 SQLite 属于两个事务域，执行后结果事件不能与用户数据库提交形成原子事务，API 因而显式返回结果事件是否落账；后续必须补充对账与恢复。当前 SHA-256 链没有密钥、外部锚点或 WORM 存储，只能发现普通修改，不能抵御拥有本地文件完全写权限且能重算整条链的攻击者。调度统一入账、保留/归档、备份恢复、外部签名、角色权限和审批仍属后续范围。

## ADR-034：定时自动化只允许物理只读，调度统一入账并提供可验证离线恢复

- 日期：2026-08-17
- 状态：已接受；修正旧调度实现与 ADR-003 的冲突，并扩展 ADR-033。该决定不改变交互写入的预览、一次性确认单、数据库绑定、执行前复检和事务回滚。
- 决定：定时 SQL 在保存和执行两处都只允许单条 `SELECT/WITH`，执行必须使用物理只读连接；定时自然语言若产生写确认单，只返回需要交互确认，不得调用 `confirm_write` 自动批准。历史启用的 SQL 写任务在启动迁移中停用。调度创建、修改、删除必须先验证审计链并登记批准事件，账本异常时 fail-closed；自动/手动运行登记唯一关联的待处理与终态事件，运行结果审计维持只读 fail-open。旧 Markdown 原文日志启动时不可逆脱敏并改为哈希文件名，新索引只保留引用、类型、状态和耗时。账本按关联 ID 对写确认、语义变更、调度变更和运行做未决对账。备份必须使用 SQLite 一致性备份并同时验证事件链、count、head hash 和文件 SHA-256；HTTP 只允许创建/查询备份，恢复只通过离线脚本开放，要求预期当前 head hash、显式确认、恢复前安全备份和临时库验证。
- 原因：旧调度 SQL 直接打开读写连接，旧定时自然语言自动批准确认单，实质绕过了“所有写操作都需用户查看实际预览并显式确认”的硬约束；旧 Markdown 还复制原始 SQL、问题和结果，与脱敏账本边界矛盾。只给这些路径补事件会制造“已审计即安全”的假象，必须先消除无人写入旁路，再统一事实记录和恢复证据。
- 影响：无人值守维护写入不再受支持，旧写任务会停用；需要变更时用户必须回到对话查看当次预览并确认。旧调度原文日志的敏感内容和含任务名文件名会被移除且不可恢复。未决对账只能发现缺少终态，不能推断用户数据库提交状态；本地备份与主账本处于同一权限域，不是异地备份、外部签名或 WORM。恢复必须在桌面应用完全退出时运行。角色权限、审批策略、保留/归档、自动异地备份、外部锚定、人工处置闭环和跨数据库原子审计仍属后续范围。

## ADR-035：本地角色权限以后端最小权限为准，写审批按提案风险升级

- 日期：2026-08-17
- 状态：已接受；扩展 ADR-003/ADR-033，不把共享角色 token 描述为个人账号、企业 IAM 或双人审批。
- 决定：保留现有主 token 作为 `admin`，以 `HMAC-SHA256(admin_token, local-rbac-v1 + role)` 单向派生 `viewer` 和 `operator`，派生 token 不另行持久化。中间件必须依次执行固定时间 token 匹配、同源校验和方法/路径最小角色检查；DB 外配置/服务入口默认 admin。viewer 可读取、提问、取消问答、生成图表和运行只读调度，但数据库列表不得返回本地路径、远程主机或用户；operator 可接入数据源、维护会话/语义/只读调度及拒绝写提案；删除数据源和创建审计备份只允许 admin。写批准还要读取未消费的真实提案：只有非危险 INSERT/UPDATE、dry-run `affected` 为 0–100 的提案允许 operator，DELETE、DDL、未知/非法或超过 100 行必须 admin。越权不得消费确认单。请求角色必须通过上下文进入异步自然语言审计，权限拒绝只记录角色、路由指纹、方法和策略，不记录 token 或请求原文。
- 原因：单一主 token 能阻止未授权网页访问，但不能区分只读查看、工作区维护和真实数据库写入；只在前端隐藏按钮既可绕过，也无法让审计说明谁以什么权限批准。将审批依据绑定到已校验、已预览、尚未消费的提案，可在不复制 SQL/数据的前提下对删除、DDL 和大范围变更保守升级。
- 影响：新增 `db_access_control.py`、`/db/auth/context`、角色管理 CLI、`access_control` 审计分类和桌面角色文字/禁用态。现有启动器继续使用 admin token，无兼容中断；viewer/operator 可通过显式发行命令取得派生凭据。当前同一角色 token 的使用者仍共享一个审计主体，没有个人身份、独立过期/吊销、设备绑定、按库/表/字段授权、双人审批或外部身份提供方；轮换主 token 并重启会同时撤销全部派生 token。前端禁用只改善可理解性，不属于安全证明。

## ADR-036：独立本地凭据只存哈希并强制生命周期，凭据变更受审计门禁

- 日期：2026-08-17
- 状态：已接受；扩展 ADR-033/ADR-035，保留既有共享角色 token 兼容，不把本地标签描述为外部身份认证。
- 决定：个人凭据使用 `id_` 前缀的高熵随机 token，独立 SQLite 只保存 SHA-256 token 哈希、显示名称、角色、创建时间、到期时间和吊销时间；有效期必须在 1–8760 小时，过期或吊销后每次请求都由服务端拒绝。原始 token 只在发行响应显示一次，列表、审计和日志不得返回 token 或哈希。HTTP 中间件先固定时间匹配共享角色，再查询独立凭据，并把凭据短引用放入请求上下文和本地操作审计。发行与吊销只允许管理员；API 与离线 CLI 都必须先验证审计链并登记批准事件，再变更凭据目录并追加终态，账本异常时 fail-closed。凭据生命周期双事件加入未决对账。
- 原因：共享角色 token 可以表达最小权限，却无法区分同角色的不同使用者，也无法只撤销一份访问权。高熵 token 加仅哈希持久化降低凭据库泄露后的直接复用风险；强制到期和不可逆单条吊销缩小长期共享风险；把凭据变更纳入审计门禁避免出现未记录的权限发行旁路。
- 影响：新增 `db_identity_store.py`、管理员凭据 API、`manage_local_identities.py` 和桌面折叠式凭据管理。自然语言异步审计可区分 `credential_ref`，但 actor 仍保留角色维度。凭据名称由本地管理员自行声明，没有密码验证、MFA、设备证明、外部 IdP、按库/表/字段授权或双人审批；拥有本机文件完全权限者仍在同一 OS 信任域。身份数据库丢失会让独立凭据全部失效，这是保守失败，不等同于可恢复的企业身份目录。

## ADR-037：外部审计锚点绑定历史前缀，但不冒充签名或 WORM

- 日期：2026-08-17
- 状态：已接受；扩展 ADR-033/ADR-034，不改变追加式账本、本地备份或离线恢复协议。
- 决定：锚点 JSON 只保存格式/schema、随机 ID、创建时间、事件数、当时 head hash 和规范载荷 SHA-256；创建前必须验证当前完整链，输出目录必须由离线管理员显式指定且不能位于审计受管目录。验证时先校验锚点结构和载荷哈希，再校验当前完整账本，并比较锚点事件数对应序号的事件哈希；当前账本可以继续增长，但不能少于锚点或改变已锚定前缀。只通过离线 CLI 暴露创建/验证，不增加任意路径 HTTP 写入。
- 原因：同机前向哈希链可以发现普通篡改，但拥有文件完全权限者能够重写全部事件并重新计算整条链；同机备份也可能被同步替换。把当时的 count/head hash 收据复制到独立保护位置后，重算后的历史前缀无法匹配旧收据，同时无需把敏感事件内容复制到外部。
- 影响：`manage_audit_ledger.py` 增加 `anchor/verify-anchor`，回归覆盖账本增长、锚点篡改、受管目录拒绝，以及本地整链重写后 `verify_chain` 通过但前缀锚点拒绝。锚点没有密钥或第三方时间戳；若攻击者也能改写锚点文件，就能同步重算载荷 SHA-256，因此只有实际存入独立受保护介质、远程不可变系统或后续签名服务才提高攻击成本。当前不是自动异地备份、签名、WORM 或保留/归档策略。

## ADR-038：个人凭据数据库范围使用稳定引用并在服务端覆盖直接与间接入口

- 日期：2026-08-17
- 状态：已接受；扩展 ADR-035/ADR-036，不把数据库范围描述为表、字段、行级策略或外部身份授权。
- 决定：独立个人凭据必须携带 `all` 或非空 `restricted` 数据库范围；范围项使用稳定数据源标识经带版本域 SHA-256 得到的 64 位引用，不持久化或返回数据库路径、远程主机、用户名、密码。新 HTTP 发行必须显式选择范围，受限引用必须对应当前已接入数据库；离线 CLI 必须显式选择全库或逐项引用。服务端在角色门禁之后检查 query/JSON 中的 `dbId`，并由 run、session、schedule ID 反查绑定数据库；列表型数据库、会话和调度接口必须过滤，按库审计只返回授权数据库，范围外对象统一按不存在处理。候选本地/远程/上传数据源只有其稳定引用已授权时才注册。受限 admin 不得管理全局凭据目录或全局审计备份，防止自行升级到 `all`。共享角色 token 保持全库兼容；v1 个人凭据迁移为显式 `all`，不得在升级时静默撤销。
- 原因：只过滤数据库下拉框不能阻止通过已知 run/session/schedule/confirm ID、审计导出或接入接口访问范围外数据；把易变 `dbId` 存入凭据又会在重启/重新接入后失效，保存明文路径/主机会扩大敏感元数据泄露。受限 admin 若仍能发行全局凭据，也会让数据库范围形同虚设。稳定脱敏引用、后端统一门禁和列表过滤共同构成可测试边界；保守迁移避免安全功能升级本身造成不可预期停机。
- 影响：`db_identity_store.py` 升级 schema v2，`desktop_bridge.py` 增加数据库范围上下文、ID 反查门禁与列表过滤，凭据 UI/CLI 增加显式范围。范围拒绝只审计凭据短引用、角色、路由引用、范围模式/数量，不记录数据库明文。当前没有表/字段/行级策略、范围在线修改、外部 IdP/MFA、管理员委派或双人审批；既有 v1 和共享 token 仍是全库，管理员需主动吊销并换发受限凭据。范围中间件预读 JSON 时必须让 handler 复用 aiohttp 缓存正文，不能把安全检查变成请求体丢失。

## ADR-039：本地 SQLite 表范围必须由执行层 authorizer 强制，不能只隐藏 Schema

- 日期：2026-08-17
- 状态：已接受；扩展 ADR-036/ADR-038，不把本地 SQLite 实现外推为远程数据库、字段或行级授权。
- 决定：独立个人凭据可在非空数据库范围内，为单个或多个本地 SQLite 数据库分别声明非空表集合；未声明表集合的已授权数据库仍是全表。表受限 `DBAgent` 只发现和采样授权表，清除指向未授权表的外键元数据和原始建表 SQL，不进入按 `dbId` 共享的 Agent 缓存。所有实际数据读取必须在 SQLite 连接安装 authorizer：包括普通 SQL、CTE/子查询/JOIN、RAG 召回；dry-run 与最终写事务还要限制 INSERT/UPDATE/DELETE 的真实目标，因此触发器、级联或读取源不能越界。表受限凭据禁止 DDL。数据库/表列表、图表和语义目录按表过滤；语义导入令牌绑定数据库、目录版本和表范围指纹。会话与运行绑定数据库+排序表集合指纹，表受限主体只能操作相同指纹对象，全表主体可以读取其权限子集创建的对象。调度、数据库级审计和整库摘除无法证明只作用于授权表，对表受限凭据 fail-closed。范围外对象统一按不存在处理，审计只记录表范围库数/表数，不记录表名。
- 原因：只从提示词或界面隐藏表，不能阻止模型生成 CTE/JOIN、写 SQL 通过子查询读取其他表、触发器/级联修改其他表，RAG 直连也会绕过 `SQLSecurity`。按请求共享缓存还可能把一个主体的宽 Schema 复用于另一个主体。SQLite authorizer 在语句编译/执行阶段看到真实读写对象，能把这些语法变体收敛到同一个可测试边界；对缺少等价机制的路径保守拒绝，比未经验证地宣称支持更符合项目门禁。
- 影响：`db_identity_store.py` 升级 schema v3，`db_sessions_store.py` 增加 `access_scope_ref` 并把旧会话迁移为 `all`；核心、bridge、凭据 UI/CLI 和审计白名单同步扩展。HTTP 发行会按当前真实 SQLite Schema 验证表名；离线 CLI 只验证范围结构，不能声称数据库在线验证。MySQL/PostgreSQL 表范围当前拒绝；授权 FTS 虚拟表若依赖内部影子表可能被 authorizer 保守拒绝。仍无字段/行级策略、范围在线修改、外部 IdP/MFA、管理员委派或双人审批；共享 token 以及未声明表范围的既有凭据保持全表兼容，管理员需主动换发最小范围凭据。

## ADR-040：本地 SQLite 字段范围同时约束元数据、读取条件和真实写目标

- 日期：2026-08-17
- 状态：已接受；扩展 ADR-039，不把本地 SQLite 字段实现外推为远程数据库或行级授权。
- 决定：独立个人凭据只有在已显式限定本地 SQLite 表时，才可把其中部分表进一步声明为非空字段集合；没有字段集合的授权表仍是全字段。Schema 必须在值域采样前移除隐藏字段，清除指向隐藏目标字段的外键元数据和原始建表 SQL。所有普通查询、确定性查询和 RAG 最终都经过 SQLite authorizer 的真实 `READ(table,column)`；直接图表和类型采样必须使用显式授权字段投影并安装相同只读边界。语义目录只显示能在过滤后 Schema 上重新校验的定义，字段外定义不能出现在 invalid 原文，也不能通过猜测 ID 或同名导入被覆盖。会话、运行、语义导入令牌和写确认单绑定表+字段规范集合指纹；没有字段限制时继续使用既有表级 v1 指纹，避免升级造成历史对象失联。
- 决定：字段受限 UPDATE 由 authorizer 同时限制目标字段和 WHERE/子查询读取字段；INSERT 因 SQLite 的 `SQLITE_INSERT` 只报告表名，必须显式列出目标字段并先经白名单校验，随后仍由 authorizer 阻断源查询、RETURNING、触发器或冲突更新越界。DELETE 没有逐字段写回调且会删除包含隐藏字段的完整记录，因此字段受限凭据直接拒绝 DELETE；DDL 同样拒绝。`COUNT(*)` 在授权表上允许，因为 SQLite 对它发出空字段名的 READ 回调。预演前后快照只投影授权字段；字段受限 INSERT 不通过 rowid 或隐藏主键回读整行，但仍提供 SQL、风险和 dry-run 影响数。最终事务必须重新安装 authorizer，不能依赖预演或文本解析。
- 原因：只从 Schema 和结果列隐藏字段，仍可在 WHERE、JOIN、CTE、聚合、RAG 的 `SELECT *`、图表采样、语义过滤、RETURNING 或触发器中读取/推断隐藏值；SQLite 对 INSERT/DELETE 的 authorizer 回调又不足以表达逐目标字段策略。把可由执行层证明的 READ/UPDATE 放行，并对 INSERT 增加显式目标列校验、对 DELETE/DDL 保守拒绝，能避免把不完整解析器或 UI 隐藏误当作安全边界。
- 影响：`db_identity_store.py` 升级 schema v4，规范化保存最多 1024 个字段并保守迁移 v1/v2/v3；核心、bridge、审计计数、CLI 和桌面凭据区同步扩展。新增回归覆盖 COUNT、投影/WHERE/CTE/RAG、INSERT/UPDATE/DELETE、预演/最终写、图表、语义隐藏与覆盖冲突、会话/确认范围隔离。远程数据库仍拒绝表/字段范围；字段受限 INSERT 的预览不含整行 after 快照，DELETE/DDL 不支持；尚无行级策略、范围在线修改、双人审批、MFA/外部身份或远程等价执行门禁。共享 token 与 v1/v2/v3 个人凭据继续保持原范围内全字段，管理员需主动换发最小字段凭据。

## ADR-041：本地 SQLite 行范围使用过滤视图+authorizer，并保持完全只读

- 日期：2026-08-17
- 状态：已接受；扩展 ADR-040，只适用于本地 SQLite，不外推为远程数据库兼容或可写行策略。
- 决定：行范围只能建立在显式数据库+表范围上，采用结构化 `column/operator/value` 条件，单表最多 4 条并只用 AND 组合；不接受 SQL 文本、OR、函数或任意表达式。受控操作符为等于/不等于/大小比较、IN/NOT IN 和 null 判断，值只允许有界标量或有界标量列表。策略字段按物理 Schema 验证，可以不在可见字段集合中。
- 决定：每条只读连接先为受限表创建连接内 TEMP 同名视图，视图显式投影可见字段并从 `main.table` 应用受控谓词；随后 SQLite authorizer 只在回调来源为该同名视图时允许读取基表及策略所需内部字段。用户显式访问 `main.table`、用 CTE 包装直读、读取隐藏策略字段或调用表值 PRAGMA 元数据均拒绝。Schema 行数/样本、SQL、RAG、图表和类型采样必须使用这一物理边界，不能只在生成 SQL 时附加 WHERE。
- 决定：行级凭据完全只读，不区分其角色标签。`WriteSecurity` 对所有 DML/DDL 直接拒绝，鉴权上下文关闭两类写批准能力，写确认范围检查拒绝行级主体。表/字段/行规范集合进入新的 `dbagent-row-access-v1` 指纹；没有行限制时继续使用既有表级/字段级指纹。v1–v4 凭据迁移后保持原范围的全部行语义。
- 原因：只把行条件附加到模型 SQL 会被 `main.table`、子查询、RAG、图表或未来新读取入口绕过；仅靠 SQLite authorizer 又无法表达“允许同表的部分行”。TEMP 过滤视图提供可组合的行集合，authorizer 的 `source` 回调把可信视图内部读取与用户直读基表区分开。行级写入还需要证明策略字段变化、并发更新、预览到确认间复检和 INSERT 新行归属，当前没有足够证据，故保守保持只读。
- 影响：身份库升级 schema v5，并扩展 HTTP、离线 CLI、审计计数、范围指纹和桌面配置。桌面当前一次配置一条条件，API/CLI 每表最多 4 条；远程数据库拒绝表/字段/行范围。现有调度、数据库级审计和整库摘除对数据受限凭据仍保守拒绝。该实现不提供外部身份核验、MFA、双人审批、远程等价强制或可写行策略。

## ADR-042：未决事件只能追加人工处置，不改写历史或伪造自动终态

- 日期：2026-08-17
- 状态：已接受；扩展 ADR-035 的未决对账，不改变跨数据库非原子边界。
- 决定：管理员可以对当前仍在未决集合中的批准/待处理事件追加 `audit_control/resolve_pending` 事件。处置必须绑定原事件序号、数据库引用和 correlation ID，结论仅允许“已核验无变更”“已核验完成”或“已由后续操作替代”。原事件和已有链不更新、不删除；自动终态已经闭合、重复处置、跨库序号或伪造无效结论均不能从未决集合移除。
- 决定：每次人工处置必须提供外部工单号或核验引用，但账本只保存其 SHA-256，不保存原文、路径或自由备注。账本完整性异常时处置 fail-closed；HTTP 只允许管理员且要求当前授权数据库，离线 CLI 还要求固定确认短语。对账结果单独报告人工处置数量，不把它混入自动成功/失败终态。
- 原因：跨数据库提交无法通过本地 SQLite 审计账本原子覆盖，进程崩溃会留下真实但无法自动判定的批准/待处理事件。直接修改原事件会破坏追加式证据，伪造 `succeeded/failed` 又会把人工判断冒充系统事实。追加独立处置、绑定外部证据指纹并保留原未决来源，能形成可追溯的运营闭环而不越过证据边界。
- 影响：审计白名单新增处置序号、结论和证据哈希；`db_audit_store.py`、权限协议、HTTP、离线管理脚本和桌面审计页同步扩展。人工处置仍不能证明用户数据库最终状态，也不替代保留/归档、自动异地备份、密钥签名、远程 WORM、双人审批或真正跨数据库原子事务。

## ADR-043：保留期先做非破坏性前缀归档，不自动删除追加式账本

- 日期：2026-08-17
- 状态：已接受；扩展 ADR-036 的外部锚点，不授权自动删除或外部系统写入。
- 决定：保留期只评估从序号 1 开始、整体早于截止时间的连续历史前缀，允许 30–3650 天，默认桌面提示口径为 365 天。评估返回推荐终止序号和 `destructive_action=false`，不移动、截断或删除当前账本。归档目标必须由离线管理员显式指定，且不能位于审计受管目录。
- 决定：外部归档采用版本化 JSON，保存完整脱敏历史前缀、每条既有事件哈希、前缀 head hash 和整个归档载荷 SHA-256；同目录随机临时文件写完后原子替换。验证时先检查格式/载荷/归档内部前向链，再验证当前完整账本及相同终止序号的 head hash。浏览器只显示待归档数量，不获得任意文件系统写路径；创建与验证只在离线 CLI 开放并要求固定确认。
- 原因：直接从追加式前向链删除旧事件会破坏 genesis 到当前 head 的验证能力，并需要新的可信检查点、外部副本确认、恢复协议和明确数据删除授权。当前没有用户指定的独立目标，也没有签名/WORM 服务。先生成可独立验证且与当前前缀绑定的非破坏性归档，可以完成可移植历史封装，同时避免把“达到天数”误当成可安全删除。
- 影响：新增 `retention-status/archive/verify-archive` 离线命令和桌面待归档提示。归档 JSON 没有密钥签名；若与账本保存在同机同权限域，攻击者仍可同步改写两者。该阶段不提供自动异地复制、自动删除、WORM、可信时间戳、恢复演练编排或法律保留策略执行。

## ADR-044：恢复演练只在隔离目录物化备份，不替换当前账本

- 日期：2026-08-17
- 状态：已接受；扩展 ADR-034/ADR-043，不改变真实离线恢复协议，也不授权浏览器任意路径写入。
- 决定：恢复演练必须先复验本地备份清单、文件 SHA-256 和事件链，再使用 SQLite backup API 把该备份物化到管理员显式指定的非受管隔离目录。临时恢复库的事件数和 head hash 必须与源备份一致；当前账本在演练前后必须通过完整链校验且事件数/head hash 完全不变，检测到并发增长或变化时不生成成功报告。演练不调用真实恢复、不替换当前账本、不删除备份。
- 决定：临时恢复数据库在校验后立即清除，只原子保留版本化报告。报告保存源备份 ID/创建时间/数据库 SHA-256、恢复副本 SHA-256、事件数/head hash、当前账本点时状态和明确的 `live_ledger_unchanged=true`、`restored_artifact_retained=false`、`destructive_action=false`，并以规范载荷 SHA-256 检查普通篡改。复验报告时必须重新验证仍可用的源备份；功能仅由要求固定确认短语的离线 CLI 暴露，不新增 HTTP 演练或恢复接口。
- 原因：已有真实离线恢复会原子替换当前账本，即使有安全备份也不适合用于常规可恢复性检查。把备份实际还原到隔离临时库并执行与真实恢复相同的链校验，可以发现“文件存在但不能可靠物化”的问题，同时把生产状态变化降为零。清除临时库减少第二份审计数据长期残留，报告则保留可追踪的点时结果。
- 影响：新增 `drill-restore/verify-drill` 和对应回归。报告只有无密钥 SHA-256，不是数字签名或第三方时间戳；源备份删除后不能完成强复验。当前只在 Windows 临时目录验证本地 SQLite，不代表指定外部介质、灾备主机、周期调度、RTO/RPO、生产切换或远程数据库已经验证。要自动向外部目标复制或周期演练，仍需用户明确配置目标、凭据、运行窗口和保留策略。

## ADR-045：外部审计备份必须可脱离当前账本独立校验和恢复

- 日期：2026-08-17
- 状态：已接受；扩展 ADR-034/ADR-044，不授权自动外部写入、HTTP 任意路径或未经确认的覆盖恢复。
- 决定：已经通过本地清单、数据库 SHA-256 和事件链校验的备份，可由离线管理员显式导出为单个 `dbagent-audit-external-backup` ZIP。包内只能存在根目录 `manifest.json` 与 `audit.db`，均必须未加密且使用 `ZIP_STORED`；额外/重复/路径穿越条目、压缩内容、超限清单和数据库大小异常一律拒绝。清单固定保存格式/版本、随机 bundle ID、创建时间、源备份 ID/时间/原因、数据库文件名/SHA-256、事件数/head hash，并以规范载荷 SHA-256 检查普通篡改。输出目录不得位于审计受管目录，写入使用同目录临时文件后原子提升。
- 决定：外部包验证不得读取或依赖当前账本，也不得要求原受管本地备份仍存在；验证器将数据库流式物化到系统临时目录，复验文件 SHA-256 和完整事件链后清理。外部包可作为恢复演练来源；v2 演练报告只保存 `external_backup` 来源和 bundle ID，不保存路径，复验时必须由管理员再次提供包。第四十阶段无来源字段的 v1 报告继续按本地备份验证。
- 决定：外部包真实恢复仅通过离线 CLI 开放，必须同时提供固定确认短语和预期当前 head hash，并复用恢复前安全备份、临时恢复库链校验、独占检查、原子替换和恢复后复验。当前账本文件缺失时允许初始化空账本并以 genesis head 恢复；当前事件链异常时仍 fail-closed，不自动覆盖尚未隔离的异常证据。
- 原因：受管目录中的本地备份与当前账本同属一个故障和权限域，原本地备份丢失后第四十阶段报告也无法强复验。单一严格包让数据库和清单作为一个可移动对象复制，并允许在当前账本不可用时独立验证。拒绝压缩和任意 ZIP 条目可以避免压缩炸弹、路径穿越和非预期文件处理；继续复用 current-head 与安全备份门禁，防止“灾备”成为静默回滚旁路。
- 影响：新增 `export-backup/verify-external-backup/drill-external-restore/restore-external`，并扩展 `verify-drill`。外部包和清单没有密钥签名或可信时间戳，只有实际复制到独立受保护介质才降低同域损坏风险；本阶段不是自动异地复制、远程目标管理、WORM、周期演练、RTO/RPO 或生产切换验证。链损坏恢复仍需后续设计“先隔离原 DB/WAL/SHM、绑定原文件指纹、再显式恢复”的单独协议。

## ADR-046：损坏审计账本必须先绑定现场并保全证据，再走独立恢复通道

- 日期：2026-08-17
- 状态：已接受；扩展 ADR-034/ADR-045，普通恢复的完整链 fail-closed 行为不变，不授权 HTTP 恢复、在线自愈或无证据覆盖。
- 决定：当前链异常时，管理员先通过离线只读评估获得版本化 assessment token。评估必须同时记录当前 DB、WAL、SHM 中实际存在文件的固定角色/归档名、字节数和 SHA-256，并把文件清单、链校验结果、错误类型/序号指纹纳入规范令牌。为避免 SQLite 即使以只读方式打开 WAL 数据库也创建或改变附属文件，链校验只能在原文件的隔离临时副本上执行；复制前后实时文件集合、大小或哈希只要变化，就要求完全退出桌面应用后重新评估。
- 决定：异常现场证据采用单个 `dbagent-audit-corrupt-ledger-evidence` ZIP，目标必须由管理员显式指定且不得位于审计受管目录。包内只能包含根目录 `manifest.json` 和评估时实际存在的固定名 `ledger.db`、可选 `ledger.db-wal/ledger.db-shm`，全部未加密且 `ZIP_STORED`。清单绑定评估令牌、逐文件大小/SHA-256、完整性错误元数据和规范载荷 SHA-256；创建时要求固定保全确认，复制完成后必须重新计算当前 assessment token 并独立复验包内全部条目。证据验证不得读取当前账本。
- 决定：普通 `restore/restore-external` 遇到链异常继续拒绝。专用 `restore-corrupt-external` 只在离线 CLI 开放，要求最新 assessment token、显式外部证据目录、严格外部备份和固定 `RESTORE_CORRUPT_AUDIT_LEDGER` 确认。执行顺序固定为：验证恢复源、生成并复验证据包、再次匹配现场令牌、物化并验证恢复库、为原现场建立逐文件受管临时回滚副本、原子替换主库并清除旧附属文件、复验恢复链。切换后的任何异常必须尽力恢复原 DB/WAL/SHM，并重新得到同一 assessment token；正常链不得使用该异常通道。
- 原因：链异常可能代表普通磁盘损坏、未完成写入或主动篡改。直接初始化、删除 WAL/SHM 或覆盖主库会消灭定位故障所需的原始证据，也会让“灾备”绕过已有完整性门禁。稳定文件指纹提供可验证的并发变化门禁，独立证据包把异常现场留在恢复域外，专用固定确认和事后回滚则把不可逆覆盖限定为管理员明确选择的离线灾难操作。
- 影响：新增 `assess-current/preserve-corrupt/verify-corrupt-evidence/restore-corrupt-external` 和故障注入回归；不新增 HTTP 路径或后台自动恢复。SHA-256 与无密钥清单不是数字签名、WORM 或可信时间戳；若证据仍留在同机同权限域，不能抵御有权同步重写全部文件的攻击者。当前只验证本地 Windows 临时环境，仍需在真实独立介质、非测试账本副本和灾备主机上演练，才能建立 RTO/RPO 或生产切换证据。

## ADR-047：外部备份目标必须显式配置、实际探测并以最近成功状态绑定复验

- 日期：2026-08-17
- 状态：已接受；扩展 ADR-045，不授权浏览器任意路径、默认后台外写、目标文件清理或把本机目录称为异地备份。
- 决定：当前只支持一个由离线管理员配置的 `filesystem_directory` 目标。目标必须已经存在、是规范绝对路径，并且不等于审计受管目录、不是其后代也不是其祖先；系统不替用户创建或推断目标。配置采用版本化严格 JSON，保存随机 target ID、配置时间、类型、路径和规范载荷 SHA-256。首次配置和替换都要求固定确认；已有配置的替换必须显式提供当前 target ID，错误或陈旧 ID 拒绝。替换不会删除旧目录中的包或抹掉旧同步状态。
- 决定：能力探测必须由固定确认显式触发，在目标中以不可预测名称独占创建 64 字节文件、flush/fsync、同目录原子替换、逐字节读回并清理临时/提升后文件；任何阶段不一致或残留都失败。状态只把这些结果描述为当前文件系统写/读/替换/清理能力，不推断物理设备、远程性、不可变性或 SLA。
- 决定：目标同步是离线显式的一次性事务序列：读取并验证配置、创建一致性本地备份、生成并独立复验严格外部包、确认包位于目标直属目录、重新读取配置并匹配同一 target ID/目录，最后原子写入版本化“最近成功”状态。状态只保存目标 ID、源备份/包 ID、包文件名和整个 ZIP SHA-256、事件数/head hash，不重复保存绝对路径。配置漂移或后续步骤失败时，已完成的本地备份/外部包保留但不登记成功；既有成功状态保持不变。系统永不自动删除目标或本地历史。
- 决定：最近副本复验必须从当前配置目录和同 target ID 状态重建直属文件路径，重新执行外部包清单、数据库 SHA-256 和事件链验证，并同时匹配整个 ZIP SHA-256、源备份/包 ID、事件数和 head hash。目标替换后旧状态只能标记为历史保留，不能冒充新目标成功。所有能力只在离线 CLI 暴露为 `configure-target/target-status/probe-target/sync-target/verify-target-latest`，不新增 HTTP 或后台调度入口。
- 原因：每次手工传目录容易把同机临时目录误认为已配置灾备目标，也无法可靠回答“最近一次完整复制是否仍可读取”。持久 target ID 和乐观替换门禁降低静默改向风险；实际探测比仅调用 `is_dir` 更能发现权限/原子替换/清理问题；最近成功状态把目标包的整体文件指纹与事件链锚定，同时确保失败尝试不会破坏最后一份已知可验证记录。
- 影响：新增一个受管目标配置文件和一个最近成功状态文件，以及 5 个离线命令和 2 项强回归。路径只存在本地管理员配置，不进入追加式事件账本或 HTTP；状态不含绝对路径。当前实现没有调度、失败历史/告警、远程对象存储协议、凭据管理、签名/WORM、保留删除或真实独立介质验证。用户必须实际配置独立目标并授权运行窗口，才能继续验证周期同步、RTO/RPO 或生产恢复。

## ADR-048：目标健康必须同时考虑最近尝试、成功时效和包复验

- 日期：2026-08-17
- 状态：已接受；扩展 ADR-047，不自动创建周期任务或告警通道。
- 决定：每次通过确认进入目标同步后，按 target ID 追加一条版本化 JSONL 尝试记录。成功记录绑定备份/包 ID、整个 ZIP SHA-256、事件数/head hash；失败只保存异常类型、错误文本 SHA-256，以及在失败前已完整生成时的包摘要，不保存错误原文、目标路径或凭据。每行以规范载荷 SHA-256 校验，读取时严格拒绝空/破损行、重复 attempt ID、结构漂移和超过 16 MiB 的历史；不自动截断或修复。
- 决定：最近成功状态与尝试历史职责分离。失败尝试不得覆盖最后成功状态，但必须增加连续失败计数；后续成功归零。健康检查为纯只读门禁，要求当前 target ID 有历史、最近尝试成功、最近成功不在未来且未超过 1–8760 小时阈值，并重新验证最新外部包及整个文件 SHA-256。任一条件失败通过 CLI 非零退出码报告。
- 原因：只保留“最后成功”会掩盖此后的连续失败；只看最近尝试又不能证明已落地包仍可恢复。把追加尝试、成功锚点、时间新鲜度和独立包复验联合起来，才能给外部任务计划或监控提供保守健康信号，同时不引入未经授权的后台写入。
- 影响：新增 `target-history/check-target-health` 和 1 项强回归。历史与状态仍只有无密钥 SHA-256，不能抵御同权限域完整重写；CLI 退出码不是远程告警、签名/WORM、可信时间戳、实际周期执行或 RTO/RPO 证明。

## ADR-049：旧 Excel `.xls` 不进入上传链路，统一提示转换为 `.xlsx`

- 日期：2026-08-18
- 状态：已接受；明确 Excel 上传格式边界，不引入新的旧格式解析依赖。
- 决定：桌面文件选择器只提供 SQLite、CSV 和 `.xlsx`；若通过脚本、拖放或非标准客户端提交扩展名大小写不敏感的 `.xls`，前端提示“先转换为 `.xlsx`”，bridge 必须在 multipart 文件内容落盘之前返回 HTTP 415。Excel 自动转库分支只接受 `.xlsx`，不得把异常捕获后的“文件已上传但未接入”当作旧格式支持。
- 原因：当前便携运行时固定使用 `openpyxl`，它明确不读取旧二进制 `.xls`，且运行时没有 `xlrd`。保留入口会让用户在完成大文件上传后才看到底层依赖异常，也使“Excel 支持”承诺与真实运行能力不一致。为了单个旧格式增加解析依赖会扩大供应链、样本兼容和安全验证范围，当前没有对应收益与门禁证据。
- 影响：`.xlsx`、CSV 和 SQLite 既有上传行为不变；旧文件必须先由用户在可信办公软件中转换。回归同时检查选择器精确扩展名、可读提示、大小写 `.XLS` 的服务端拒绝以及拒绝前无文件落盘。未来若要恢复 `.xls`，必须获得用户明确授权、锁定解析依赖、增加隔离样本和资源上限验证，并用新 ADR 取代本决定。

## ADR-050：默认桌面采用单机所有者体验，角色协议退居后台安全兼容层

- 日期：2026-08-18
- 状态：已接受；只改变默认桌面交互，不取消鉴权、数据库范围、写入预览或显式确认。
- 决定：由启动器打开的日常桌面统一显示“本机模式”，不向用户展示查看者/操作员/管理员名称，也不在审计工作台展示个人凭据发行区。写入预览直接说明“受控变更/高风险变更”、影响范围和执行前复检，不要求单机用户理解角色审批术语。
- 决定：主 bridge token、同源/Cookie 鉴权、`local-rbac-v1`、个人凭据、数据库/表/字段/行范围、服务端能力矩阵及离线管理脚本继续保留。已有受限 token 仍按原权限执行，不能因界面统一而升级；危险写入仍必须通过预览、一次性确认单、服务端复检和审计门禁。

## ADR-051：自动图表按表持久缓存，仅由数据库指纹变化或手动刷新失效

- 日期：2026-08-18
- 状态：已接受；当前只适用于本地 SQLite，不把文件元数据指纹描述为内容哈希。
- 决定：每张当前可见业务表生成至多一张代表图，完整快照以稳定数据库引用和当前访问范围指纹为键持久保存；表级条目必须与快照头在同一 SQLite 事务内替换。相同数据库但不同表/字段/行范围不得共享快照。图表总数上限 128，每图聚合点继续限制为 200。
- 决定：缓存版本绑定 SQLite 主文件以及存在时的 WAL/回滚日志的大小、纳秒 mtime 和 ctime，经规范 JSON 计算 SHA-256。请求时指纹不变则直接复用；指纹变化、缓存缺失/损坏或用户显式手动刷新时重新生成。生成前后指纹必须一致，连续变化两次则拒绝落缓存，避免保存混合时点图表。
- 决定：桌面已显示的同数据库图表在缓存检查期间保留；响应仍命中同一指纹时不销毁 ECharts 实例。图表页可每 5 秒调用只返回指纹变化布尔值的轻量端点，未变化时不传输缓存图表；数据库切换、指纹变化或手动刷新才替换画面，探针失败不清空已有图表。
- 原因：自动图表聚合会随表数量增加重复读取数据库；每次进入页面都重新生成既浪费资源，也造成画面闪烁。访问范围进入缓存键是防止缓存绕过表/字段/行级授权的必要条件；生成前后双指纹可降低并发写入时缓存不一致风险。
- 影响：新增运行态 `dbagent_chart_cache.sqlite` 和缓存状态协议 `hit/generated/database_changed/manual_refresh/uncached`。文件 mtime/ctime/大小是保守更新信号，不是数据库内容的密码学证明；具有本机完全写权限者可伪造元数据。远程数据库缺少已验证的等价更新令牌，因此当前继续拒绝自动图表缓存，未来必须按具体方言验证事务可见性和变更版本后才能开放。

## ADR-052：写确认选择不得被前端缓存权限永久锁死，执行仍以服务端为权威

- 日期：2026-08-18
- 状态：已接受；扩展 ADR-003/ADR-035/ADR-050，不降低 HTTP 角色门禁、数据库/表/字段/行范围、一次性确认单、审计完整性或执行前复检。
- 决定：自然语言产生有效写预览与确认单后，桌面“确认执行/取消”必须保持可选择，不能因为页面初始化默认值、旧窗口 cookie 或前端缓存的能力矩阵直接写成永久 `disabled`。按钮点击只表达用户选择；服务端继续按实际请求主体、提案风险、确认单数据库/访问范围绑定和审计状态决定是否执行。提交期间只临时锁定当前卡片防重复请求，失败后恢复；成功确认或取消后该卡进入终态。
- 决定：确认请求绑定生成预览时的数据库 ID，不能使用点击时可能已经切换的全局数据库。401/403 必须提示从桌面图标重新建立本机工作区，404 提示确认单失效或数据库已切换。取消结果必须明确数据库未变更，不能沿用“写操作已完成”展示。
- 原因：前端状态不是权限事实源；把能力判断固化为 `disabled` 会让此前受限窗口在界面统一为“本机模式”后既不能操作，也无法理解恢复方式。另一方面，单纯移除服务端门禁会把体验修复变成写安全回退。可点击选择＋服务端权威复检同时解决死锁和安全边界问题。
- 影响：前端不再把 `roleCan(...)` 结果用于永久禁用写确认选择，但仍可用于说明文案；`POST /db/write/confirm` 的最小角色保持 operator，高风险批准仍由 handler 升级为 admin，越权不消费有效提案。回归必须同时验证按钮可选择、提交期防重复、失败恢复、确认真实提交和取消零写入/一次性消费。

## ADR-055：公开模型基准与离线完成门禁隔离，评分口径和生产安全口径分开报告

- 日期：2026-08-20
- 状态：已接受；扩展 ADR-012/ADR-032，不授权 benchmark 绕过关系澄清、写确认、访问范围或只读安全边界。
- 决定：公开真实模型 benchmark 必须固定上游仓库提交、数据文件 SHA-256、抽样策略/seed、样本指纹、Prompt 指纹、脱敏模型身份和独立评分契约；逐题生成 SQL、公开问题数据、合成数据库和检查点只保存在 Git 忽略目录，不保存密钥或原始接口地址。公开 benchmark 只有显式运行才访问模型，默认离线门禁不调用外部服务，也不把单次公开分数写成完成门禁通过率。
- 决定：Spider 1.0 schema-only 通道使用官方 dev 问题/schema/评测代码、按难度与数据库轮转的固定样本、schema-faithful 空 SQLite 和生产 NL2SQL/只读执行链。没有官方数据库内容时，只报告官方忽略值 Exact Set Match、官方旧 AST 覆盖率、生产生成/执行成功率与延迟；必须明确不是 Execution Accuracy、Test Suite Accuracy 或官方排行榜提交。评分适配只能处理不改变结果值的解析器表面差异，并保留原始 SQL；其他等价结构不能在无真实数据验证时自动改写为通过。
- 决定：基准暴露出的 schema 固定截断按生产问题修复：总列数不超过 384 的 schema 完整进入上下文；更大 schema 在一个全局列预算内优先问题命中列、PK/FK，继续展示所有表名和省略计数。提示可要求优先简单直接 SQL，但不得为了 benchmark 强制采用可能降低真实正确性或方言兼容性的写法。
- 决定：未声明关系导致的 `table_relationship` 澄清在 Spider 中仍计失败，但产品不为得分猜测 JOIN。后续 BIRD CRUD 等写基准只能测试计划、校验和预览；实际提交仍要求用户显式确认，禁止 benchmark 自动确认落库。
- 原因：单一小型合成题集无法衡量跨领域 schema linking 和复杂 SQL；但公开 benchmark 的旧解析器、数据许可、在线模型波动和产品安全门禁又与真实产品正确率不同。固定生成契约、评分契约并分开展示生产可执行率/解析覆盖率，可以让差距可复现，同时避免把合法等价 SQL误判成产品不可用或为刷分削弱安全。
- 影响：新增 `scripts/run_spider_benchmark.py/.cmd` 与 `docs/BENCHMARK_REPORT.md`，公开数据和运行结果目录进入 `.gitignore`；门禁只编译 runner 和运行其无网络回归，不下载公开数据、不请求模型。首个固定 100 题结果为优化前 46/100、优化后 48/100 Exact Set Match，生产只读链均为 98/100；该单次 +2 伴随 6 题改进、4 题回归，尚需重复运行、真实 Spider 数据库 Test Suite Accuracy、Spider 2.0/BIRD/LiveSQLBench 和真实 MySQL/PostgreSQL 验证，不能外推为普遍准确率。

## ADR-056：NL2SQL 语义纠偏采用高置信局部反馈，不全局堆叠规则或直接改写 SQL

- 日期：2026-08-21

- 决定：只对可由问句/schema/生成 SQL 交叉验证的偏差追加局部反馈并复用既有最多两轮自纠错。
  当前覆盖五类：一是从问句输出短语识别明确请求的简单列，发现多余或遗漏投影；二是问句用
  AND/和/与连接两个明确值，而 SQL 用没有 `HAVING`、双 `EXISTS` 或交集的裸 `IN` 表达“任一值”；
  三是同一事实表存在名称可识别的 source/destination 两个已声明 FK 指向同一实体时，提示未限定
  角色的总体统计需要覆盖两侧，并避免对已聚合分支使用外层 `COUNT(*)`；四是当时间列真实抽样值证明
  `YYYY-MM-DD` 月份位置、斜杠格式或“时间戳列对纯日期等值”与存储格式冲突时，给出具体存储证据；
  五是当等值字面量与唯一真实抽样枚举值仅大小写不同时，要求使用抽样值的精确大小写。
  跨表关系门禁必须先于语义重试，缺少已声明/显式关系时立即澄清，不能让模型借重试改写绕过。
  不对 SQL 做字符串级自动改写；该阶段最终一次仍未改正时沿用既有查询执行行为，后来经 BIRD
  证明“可执行不等于语义正确”后由 ADR-057 改为持续冲突拒绝执行。它始终不是形式化正确性验证器。
- 决定：主提示继续保持简洁。把投影/集合规则全局加入主提示的两版固定 100 题实验分别为 47/100 和 42/100，均不保留；最终仅在命中高置信偏差时把具体错误反馈给重试。公开 benchmark 的 Prompt 契约必须哈希完整 `NL2SQLExecutor` 与 schema 问题上下文源码，不能只哈希首轮提示字符串，避免动态提示、辅助判断或重试逻辑变化后复用旧检查点。
- 原因：Spider 失败中既有真实漏列/多列/集合语义错误，也有 `NOT EXISTS`、标准 GROUP BY、CTE、CAST 等合法等价 SQL 被旧解析器计零。全局规则会扰动大量无关样本并增加模型长尾；直接重写投影或集合结构又可能改变 DISTINCT、去重、分组和方言语义。局部、具体、可回归的反馈能修复明确产品缺陷，同时保留模型根据完整 schema 重新生成的责任边界。
- 影响：关系门禁优先级审查后的最终固定 100 题为 47/100、生产只读链 98/100，相对上一版 3 题转对、4 题转错，净减 1；旧 AST 72→74，中位/P95/最大延迟 4.303/44.953/88.049 秒变为 5.143/69.734/251.405 秒，不能宣称分数或性能改善。定向与最终样本确认输出短语、跨记录 AND 和双角色统计得到改善，关系门禁两题仍直接澄清，但 `official language` 与 `IsOfficial` 等形容词/布尔列边界仍会漂移。同一最终契约仍需至少三次重复运行、真实数据库执行准确率和业务数据验证。
- 2026-08-21 BIRD 扩展影响：固定 60 题完整运行为 34/60 EX；后续枚举大小写与日期对时间戳两类
  新反馈在 `1484/1338` 生产增量重放均通过，已知组合增量为 36/60。它不等于最新生成契约已重跑
  60/60；同契约完整重跑和至少三次重复仍是必需证据。

## ADR-057：NL2SQL 从直接 SQL 生成升级为“查询合同→SQL→本地验收→执行”

- 日期：2026-08-21
- 状态：已接受；扩展 ADR-032/ADR-055/ADR-056。不改变关系澄清、只读单语句、访问范围、行数上限或写确认边界。
- 决定：首轮生成必须同时返回版本化查询合同和 SQL。合同显式声明按顺序的输出、每行粒度、筛选、分组、关联、排序与条数；用于审计和语义诊断，不作为绕过 `SQLSecurity` 或关系门禁的授权。模型未按新协议返回合同时仍可按兼容路径处理 SQL，但 benchmark 必须单报合同覆盖率。
- 决定：schema grounding 不只给物理名。通用 `DBColumn` 允许承载业务名、列定义和值定义；只有与当前问题高相关的有界片段才进入模型上下文。schema 抽样值不会全量发给外部模型；只反馈用户已明确提供且与抽样值匹配的规范大小写，或不含原始数据的时间存储形状。BIRD runner 可导入官方公开列字典和 `dev_tables.json` 已声明外键；仍不猜测未声明 JOIN。
- 决定：SQL 执行前使用高精度本地合同检查输出、并列统计、行粒度、集合、数值类型、时间形状和枚举值。本地检查器不改写 SQL；冲突最多进行一次模型修复，修复后仍冲突则返回 `query_semantics` 澄清并且不执行已知错误 SQL。曾实验只删除顶层非 `DISTINCT` SELECT 中的多余纯列，但 BIRD 完整运行 6 次触发只有 1 次 EX，并直接造成 coordinates、which-user 和 legalities-status 三类回归；因此该例外已撤回，不进入生产主链。
- 决定：不对所有可执行复杂查询调用第二模型复核。BIRD 60 题消融中，全量复核仅从 34/60 到 35/60，却出现 3 题回归，且 P95/最大生成延迟达 477.756/574.533 秒；“只复核空结果复杂查询”的消融为 34/60，仍有明显模型波动。因此二次复核只保留为空结果异常的有界执行反馈；复核不可用成功执行替代语义正确证据，复核失败不丢弃已通过只读安全的原候选。
- 决定：公开基准至少分开报告自动金标命中、修复后接受、已知冲突被拒绝、关系门禁、可执行率和延迟。“拒绝执行已知错误 SQL”是安全改进，但在 Spider/BIRD 自动准确率中仍计失败，不与金标命中相加。
- 原因：BIRD 旧契约有 58/60 生产查询成功却只有 34/60 EX，证明“能生成/能执行”不是产品终态。仅用更长主提示、更多重试或第二模型改写会增加方差和长尾，不能形成可审计的语义边界。类型化合同、有界 grounding、高精度本地验收和 fail-closed 执行顺序才是可回归的架构分层。
- 影响：当前 BIRD 契约 `nl2sql-e855315a0608b005` 完整 60 题为 EX 37/60、严格行序
  34/60、生产查询 56/60；相对旧完整 34/60 为 7 题转对、4 题转错。合同覆盖 60/60，
  一次修复后接受 8、持续冲突拒绝 2。当前 Spider 契约 `nl2sql-d773193acd8dc496` 完整
  100 题为 Exact 43/100、生产 SQL 97/100、旧 AST 65/100；相对旧 47 分为 1 题转对、
  5 题转错。架构改善没有形成跨 benchmark 总分普涨，下一步必须将合同编译为独立关系代数
  约束并补真实 Spider 执行评分，不能继续依赖同一模型自报意图或堆叠 Prompt。
- 影响：OpenAI 兼容 base URL 以 `/v1` 结尾时必须继续拼接实际 endpoint，不能把 `/v1`
  当成最终请求地址；对应客户端缺陷已修复并回归。第二模型凭据/服务错误与模型质量分开记录，
  本机秘密配置不进入源码、benchmark 原始结果或文档。

## ADR-058：在模型之前编译独立关系代数合同，低置信形状不自动约束或改写 SQL

- 日期：2026-08-22
- 状态：已接受；扩展 ADR-057，不改变关系门禁、SQLSecurity、访问范围、行数上限、写确认或公开 benchmark 评分口径。
- 决定：新增版本化 `RelationalAlgebraContract 1.0`。它必须在第一次模型调用前，只依据当前问句、物理 schema 和用户/公开数据集显式提供的业务字典编译，不能读取模型声明的 `QueryIntentContract`、候选 SQL 或 gold。当前仅为高置信模式生成可执行约束：显式业务概念映射到多个物理列时分别投影；逐实体聚合要求 GROUP BY；按关联记录数量筛选要求 GROUP BY/HAVING；明确 distinct/unique 实体计数要求去重；形式语言中的 ANY/ALL 绑定存在/全称量词与 MIN/MAX 方向；命令式“rank … by … showing …”要求返回排名列；同表 `IsOfficial` 等标志只作修饰词过滤；明确要求 ties 时禁止 `LIMIT 1` 丢并列。
- 决定：只有 `is_actionable()` 的合同才以有界 JSON 注入首轮 schema 上下文。生成后先由关系代数合同检查，再进入既有模型查询合同和局部语义检查；最多一次模型修复，仍冲突返回 `query_semantics`，不执行已知错误候选。本地层只产生具体冲突证据，不做字符串或 AST SQL 改写。未命中的问法、单一业务字典映射、未明确并列策略的极值题和复杂子查询保持未声明/仅审计状态，避免把猜测升级成强约束。
- 原因：ADR-057 的 `QueryIntentContract` 与 SQL 由同一模型同时生成，只能提供审计和自洽检查，不能作为独立正确性证据。BIRD/Spider 的主要残差已集中到输出原子、聚合键、关系数量、比较量词、修饰词和 tie 语义；继续加长全局 Prompt 或对所有查询调用 reviewer 已通过消融证明会增加回归与长尾。
- 影响：BIRD 固定 60 题当前契约 `nl2sql-9f3c03d8a117696c` 为 EX 41/60、严格行序 38/60、生产查询 56/60；相对上一查询合同 37/60 为 5 题转对、1 题转错。独立合同直接命中的 3 个旧失败全部转对；另外 2 转对/1 转错不归因于合同。Spider 固定 100 题当前契约 `nl2sql-9aa9201f1a0d9177` 仍为 Exact 43/100，相对上一 43 分为 3 转对/3 转错；旧 AST 65→68，但生产 SQL/查询 97→94，4 个持续语义冲突被拒绝。ANY 题生成的 EXISTS 在关系语义上满足合同但旧解析器计零；这说明独立算子合同不是完整 SQL 等价或聚合/连接正确性证明。
- 影响：下一层不得继续按 benchmark 样本堆专用字符串规则。需要把合同扩展为可审计的 AST/关系代数图，显式表示实体键、聚合输入、连接路径、比率分子/分母、子查询相关性和 tie 策略，并用真实执行/Test Suite 与重复运行区分表达等价、模型方差和真实产品缺陷。

## ADR-059：单个 LLM 提供商请求与重试链必须共享总截止时间

- 日期：2026-08-22
- 状态：已接受；只约束项目模型传输层的单提供商调用链，不改变 NL2SQL 语义重试上限。
- 决定：`_stream_with_retry` 在进入第一次 HTTP 调用时建立单调时钟 deadline，默认总时长 600 秒，配置值限制在 10–1800 秒。每次连接和读取 timeout 取配置值与剩余总时长的较小值；HTTP/连接/流重试退避不得越过 deadline；SSE 逐行解析和非流式 JSON 完成后也检查 deadline。超限统一返回脱敏 `!!!Error: TotalTimeout`，不得把部分错误片段和随后成功 JSON 拼接。
- 原因：一次 BIRD 全量运行跨日暂停后，4 个在途任务记录约 8500 万毫秒，污染 P95/最大值并让外部服务、宿主暂停和客户端重试难以区分。连接/read timeout 只能限制一次底层阻塞，不能限制多个 HTTP 尝试及退避的总生命周期。
- 影响：该决定只保证未来活动的单提供商请求/重试链有上限；宿主进程被冻结时不能保证墙钟准点回调，恢复后才会检测 deadline。受污染运行的准确率仍可按完成结果分析，但延迟不可与旧契约比较。mixin 外层多提供商故障转移目前仍可能由多个各自有界链累加，若未来实际启用并观测到问题，应另行增加整个 mixin 会话的共享 deadline，而不是误报本决定已覆盖。

## ADR-060：关系代数合同 1.1 验证实体键、聚合输入、全数量阈值和实际 JOIN 边

- 日期：2026-08-22
- 状态：已接受；扩展 ADR-058，不改变关系门禁、SQLSecurity、访问范围、查询行上限、写入确认或公开 benchmark 评分口径。
- 决定：`RelationalAlgebraContract` 升级为 1.1。只在问句可高置信映射到唯一 schema 事实时，声明逐实体聚合的实体主键、显式平均值的聚合函数/输入列以及问句中所有可解析的关系数量比较；验收必须同时核对 GROUP BY 实体键、聚合函数/输入、每个 HAVING 阈值、ANY/ALL 量词与比较符方向、修饰词标志实际出现在 WHERE/HAVING。合法整数等价形式如 `> 1` 与 `>= 2` 可以互认，但不用此放宽其他语义。
- 决定：表集合连通只证明 schema 图上“存在某条路径”，不再被当成候选 SQL 使用了正确 JOIN 列的证据。对不含 CTE/集合运算、别名可解析、`ON` 条件为简单列等值且 schema 具有完整直接 FK 的候选，必须校验实际列对与 FK 一致。缺元数据、表达式 JOIN、多跳路径、CTE 或用户已显式给出的等值关系保持原有保守边界，不猜测或自动改写。
- 决定：投影验收必须区分物理列别名与聚合表达式别名，保留“A and the name of B”类协调输出，并使用业务元数据中罕见概念词防止通用词使不同列相互冒充。不因评测金标新增样本 ID 分支，不对 SQL 做字符串或 AST 自动改写，仍最多一次模型修复后 fail-closed。
- 原因：1.0 可确认“存在 GROUP/HAVING/JOIN”，却不能证明分组键、聚合输入、所有数量约束和实际 ON 列正确。旧候选重放还显示投影检查曾误拒协调输出、预计寿命列和聚合别名，同时放过业务名称相似的错列。这些是通用验收层缺陷，不是单个 Prompt 可靠解决的问题。
- 影响：零模型重放旧 BIRD 60 + Spider 100 候选时，没有任何旧正确样本出现新拒绝；新完整运行的 BIRD 仍为 41/60（1 转对/1 转错，两者均不归因于新合同），Spider 为 49/100（6 转对/0 转错，只有 2 题可直接归因于本轮误拒修正）。这些结果不支持“已根治低准确率”：验收发现错误后，同一模型唯一一次修复仍可重复错误。下一层应是以独立关系代数图约束的有界多候选生成/选优和真实执行评分，不是继续按样本堆字符串规则。

## ADR-061：语义修复采用冲突条件化有界候选与本地投影编译，选择必须有独立证据

- 日期：2026-08-24
- 状态：已接受；扩展 ADR-057/058/060，不改变关系门禁、SQLSecurity、访问范围、查询行上限、写入确认或公开 benchmark 评分口径。
- 决定：首个 SQL 只有在本地高置信 `QuerySemanticConflict 1.0` 存在时才触发一次 `BoundedCandidateSearch 1.0`，一次回答最多 3 个候选。候选不是投票或自评分样本；每个候选必须独立通过分支范围、关系事实、只读单语句和本地语义合同。主修复合格时保留原有一次修复路径；主修复不合格时，仅当恰好一个不同替代候选合格才接受；多个不同候选合格或全部不合格时，因没有独立正确性裁决而返回 `query_semantics`，禁止按模型顺序、文字理由或自报置信度选一个执行。
- 决定：`RelationalAlgebraContract` 升级为 1.2，保存按输出顺序的物理 `output_bindings`。明确绑定完整时，候选协议只允许模型返回从 `FROM` 开始的 `sql_tail`；本地编译器从绑定与候选引用的表/别名确定性生成 SELECT，并拒绝不完整绑定、输出表缺失/重复引用、首源派生表和多解表归属。编译结果仍必须重新经过所有范围、关系、安全和语义门禁。该编译只发生在已被本地拒绝的修复路径，不授权对任意已接受 SQL 做 AST/字符串自动改写。
- 决定：合同合并必须满足同维度权威单调性。显式业务字典和“修饰词标志只作筛选”的关系合同拥有物理绑定时，较弱通用投影启发式不得重新增加/删除同一输出。通用输出抽取可高置信处理“实体 ID”“下划线连接的多词物理列”和“单数实体的最高/最多结果”；单数 superlative 声明 `single_row`，明确 all ties 仍优先为 `all_ties`，复数实体不为贴 benchmark 金标强制单行。
- 决定：Spider 评分兼容只作用于评分副本。除了既有表别名 `AS` 和投影别名适配，可移除“限定符 + schema 已知 + 本身可作为裸标识符”的安全双引号；字符串字面量、需引号列名和原始生产 SQL不变。派生表、EXISTS 或函数依赖 GROUP BY 被旧 Exact 拒绝时仍如实计失败，不通过无证明重写抬分。
- 原因：DeepSeek V4 Flash 在 `1179/0894` 初始诊断中生成了表面不同但共享同一错误投影的候选，并在文本提示明确列约束后继续忽略约束；这证明多样性 Prompt 不是独立正确性保证。本地投影编译后两题最终真实执行 2/2。随后固定 Spider 诊断从 2/7 暴露出实体 ID、多词列、修饰合同权威倒置和旧解析器引号四类独立缺陷；修复后最终为 4/7 Exact、7/7 可执行，`0069/0768` 有在线复测与回归共同证据。剩余派生表/EXISTS/按主键附带名称分组差距不能诚实归因为运行时语义失败或本轮修复成功。
- 影响：最终 BIRD 两个历史失败族为 2/2 Execution 与严格序列，但中位/最大生成时延 84.847/117.595 秒，候选搜索的尾延迟仍未解决。最终 Spider 7 例只是诊断集，不替代上一阶段 100 题；最近完整全量分数仍为 BIRD 41/60、Spider 49/100。下一层应把当前局部合同继续扩展成覆盖关系路径、聚合阶段、比率分母和相关性的目标 IR，并用真实执行与重复运行校准；不能把定向 100% 外推为全量或用旧 Exact 的结构偏好驱动生产 SQL。

## ADR-062：目标关系 IR 只编译可证明的路径、阶段、分母与相关键，多外键歧义不按 gold 强选

- 日期：2026-08-24
- 状态：已接受；扩展 ADR-058/060/061，不改变关系门禁、SQLSecurity、访问范围、查询行上限、写确认或公开 benchmark 评分口径。

## ADR-063：公开 NL2SQL 收益必须用同契约重复证据，问句表名路径只作条件式验收

- 日期：2026-08-24
- 状态：已接受；扩展 ADR-057/058/060/061/062，不改变关系门禁、SQLSecurity、访问范围、查询行上限、写入预览或显式确认。
- 决定：一组重复运行只有在数据 SHA-256、样本指纹/大小/seed、模型身份、Prompt 契约和评分契约全部相同时才可以合并。报告必须同时给出每轮分数、均值/样本标准差、稳定通过/失败/波动题、逐题错误和延迟长尾。事后多数/any-run oracle 只测量采样上限，不能宣称为生产选择策略。
- 决定：问句完整命中多个物理表名时，可编译 schema 中唯一最短 FK 路径，但这种路径的 `enforcement` 必须是 `when_both_tables_referenced`：候选 SQL 实际同时引用某条边的两端时才验收物理列对。它不能强制把 `INTERSECT/UNION` 的独立分支连起来，也不能为了路径完整性强加候选没有引用的桥表。多解路径仍不编译。

- 影响：同一固定 Spider 100 三次为 47/47/45，均值 46.3%、样本标准差 1.15 个百分点，稳定通过/稳定失败/波动为 41/48/11；全调用延迟中位/P95/最大为 17.476/166.990/403.356 秒。修正后零模型 IR 覆盖为 33/100，三轮旧候选 300 条反事实验收对旧通过题新增拒绝 0。这不等于新生成契约分数已提高；修正后尚未全量在线重跑。

## ADR-064：Spider 只暴露架构缺口，生产优化不得以 gold SQL 结构为目标

- 日期：2026-08-24
- 状态：已接受；扩展 ADR-055/058/062/063，不改变关系门禁、SQLSecurity、访问范围、查询行上限、写入预览或显式确认。
- 决定：Spider/BIRD 可用于定位自由 SQL 生成、schema grounding、关系路径、聚合粒度、过滤完整性、候选裁决和模型延迟等架构缺口，但 benchmark gold 的具体 JOIN 顺序、等价分组列、别名、子查询风格或旧解析器偏好不得反向决定生产计划或 SQL 渲染。生产改动必须能由问句、schema、显式业务证据、关系代数等价、真实数据库结果或安全边界独立证明，并至少有不依赖 gold 的回归夹具。
- 决定：新增 `Native Relational Planner 1.0`，把完整物理输出、唯一声明 FK 边、`COUNT(*)` 聚合和排名编译成类型化 `RelationalQueryPlan`，由 SQLite 渲染器本地生成 SQL。首版只接管整句闭世界核对通过、无未表示过滤、最大关系数量和明确 tie 策略的形状；最少关系因为需要保留零关联实体而回退，远程方言、多解/不完整合同同样回退。计划成功后仍经过访问范围、关系、语义、只读单语句和行数门禁；它不扩大写入权限。
- 决定：评分器兼容只能修改评分副本。schema 已知且本身可安全裸写的双引号表名可在 Spider 旧解析器副本中去引号，原始生产 SQL不得改变。定向 Exact、固定样本覆盖和总分均是观察指标；本地计划的主验收是类型/关系约束、真实 SQLite 结果、回退完整性和安全回归。
- 原因：Spider 三轮暴露的根因不是某一条 gold SQL 的表面结构，而是目标 IR 虽存在却没有拥有执行计划，导致关系计数题仍依赖模型生成完整 SQL，未表示过滤可能被静默丢失，尾延迟也由模型调用主导。首次定向检查还显示，语义等价的实体键/事实外键分组可能受旧 Exact 结构口径影响；因此明确禁止以该差异驱动生产渲染。
- 影响：同一固定 100 题零模型反事实中，首版计划器保守形成 2 个可执行计划；这证明一小类问题已从“模型 SQL + 本地验收”前移为“本地关系计划 + 确定性 SQL”，不证明 100 题总体正确率提升。完整回归当前 321/321；下一步应先实现类型化过滤节点和保留零事实的 outer-entity 关系计数，再扩展比率/相关子查询，而不是按 Spider 失败逐题模仿 gold。

## ADR-066：关系合同 1.5 以证据化未知态约束标量排序、类别粒度、比率总体与 tie 基数

  序列 5/5。定向和反事实回放不替代新的 Spider 100/BIRD 60 全量运行；最新完整分数仍为 54/100

  回归验证，不能只报告新增覆盖或 benchmark 金标命中。

  零模型、约 0.1 秒的产品正确结果，但旧 Exact 因它使用更稳定的主键粒度/左连接仍记失败；当前无 1.6 全量分数。

## ADR-074：大 Schema 上下文采用频率降噪、证据预留和多解拒绝

- 日期：2026-08-25
- 状态：已接受；不改变 SQLSecurity、访问范围、关系 fail-closed、查询行数、写预览或显式确认。
- 决定：总列数超过 384 时，Schema 上下文不再把任意 token 重合都视作表命中，也不允许按表顺序
  预留的主键先耗尽全部列预算。英文标识符使用保守单复数归一，同时保留原词；精确匹配按 token
  边界而不是任意子串，全库高频表/列 token 不获得稀有词权重，避免 `archive_partition_N` 一类
  系统化名称把所有表误判为问题相关。
- 决定：列预算按证据等级分配。先为最多 8 个可信问句命中表之间、最多 8 跳且唯一的最短声明 FK
  路径预留每条边的源列和目标列；再独立预留最多 64 个问句/字典相关列、命中表主键，最后才由
  评分填充剩余预算。存在并行边或两条等长路径时不生成路径权威，不能为了上下文完整度猜 JOIN。
  没有列明细的表合并为分块 `TABLE INDEX`，仍保留每个表名和省略列数；小于等于预算的 Schema
  继续无损输出全部列。
- 原因：3000 列压力中，旧架构不能把问句复数 `accounts` 链接到单数物理 token，导致
  `account_segment` 在 100×30、500×6、1000×3 三种形状中均缺失；共享的 `archive/partition`
  token 又使大量无关表获得相同加分。全局 384 列预算可被无关主键占据，也没有保证两个真正命中表
  之间的桥接 FK 列进入模型上下文。上述是大 Schema 通用召回与关系证据问题，不来自 Spider gold。
- 影响：三种 3000 列形状均保留 `customer_lifetime_value` 与 `account_segment`，同时保留首尾噪声

  中位选择时间为 43.62/55.28/68.75 ms。唯一 FK 路径在 8 列极限预算中仍保留两端 PK、桥接双 FK
  和问句列，两个等长路径的负例返回无权威。直接回归 370/370；Spider 固定旧候选回放仍为 95/4/1，
  BIRD 仍为 55/5，普通修复回归 0；原始严格/上游 TSA 保持 74/75，上游交叉校验 100/100。该压力
  只证明确定性压缩器，不冒充大 Schema 真实模型准确率。

## ADR-075：静态 Schema 链接索引按访问快照预编译并可验证失效

- 日期：2026-08-25
- 状态：已接受；扩展 ADR-074，不改变访问范围、关系 fail-closed、SQLSecurity、查询行数、写预览
  或显式确认。
- 决定：`SchemaSnapshot` 首次生成问题上下文时，预编译表/列 token、规范形态、全库频率、稀有词和
  稀疏业务字典 token；同一快照内完全相同的标识符/字典文本共享不可变分析。缓存只属于当前已授权
  SchemaSnapshot，不建立跨数据库或跨凭据全局缓存，避免范围外表名、字段或字典在不同访问上下文间
  复用。FK 图只有在至少两个可信表命中时才惰性构建，并在同一结构版本内复用。
- 决定：快照仍可在发现和授权收窄阶段原地组装，因此不能只按对象 ID 永久缓存。每次使用以稳定表
  顺序、列名、PK、FK 目标和三类业务字典元数据构造结构签名；签名变化先完整重建索引，再原子替换
  快照私有引用。字段类型和行数不参与选择索引，但渲染始终读取当前对象值。并发冷启动允许重复构建

- 原因：1000 表/3000 列的同一快照连续问答中，旧实现每问执行 7,155 次标识符分词，重复计算静态

  稀疏字典和按需关系图，而不是进程级无界 LRU。

  28.72/36.15/49.05 ms，热请求中位为 16.80/19.28/26.79 ms；目标列与上下文字符数保持不变。

  来自本机合成 Schema，不能外推为远程数据库或真实模型端到端延迟。

## ADR-076：模型正确率采用重复生成与多数据库执行分层，不以单指标驱动架构

- 日期：2026-08-25
- 状态：已接受；这是评测与架构归因规则，不改变 SQLSecurity、访问范围、关系 fail-closed、查询
  行数、写预览或显式确认。
- 决定：公开模型轮必须固定样本、Prompt、模型身份和评分契约，保存每次原始预测，并分别报告
  Exact、生产 SQL 有效性、官方解析覆盖、单发布库执行、严格产品 TSA、上游兼容 TSA 与固定上游
  逐题交叉校验。同契约重复运行必须报告稳定通过、稳定失败和候选波动；不同 Prompt、代码时间点或
  生成契约的分数不能作为单变量因果对照。基础设施失败继续不进入语义正确率分母，三轮 any-pass
  只可作事后上界，不能冒充生产选择策略。
- 决定：架构修复优先级由稳定多库语义失败决定，按“类型化 IR/合同缺口、输出或聚合粒度、关系
  证据、候选不确定性、端到端 deadline”归因。未定序并列的任意赢家、benchmark 将可见值集合与
  同一实体语义混用、或 gold 未请求投影等口径冲突必须单列，不允许为提高分数删除稳定 tie、扩大
  JOIN 权威或降低 fail-closed。单库一致只能作为中间证据，因为多扰动库能揭穿数据偶合假阳性。
- 原因：DeepSeek V4 Flash / Relational IR 1.8 的三次固定 Spider 100 从零生成得到 Exact
  43/44/43、单库执行 76/77/76，却只有严格 TSA 61/62/60、上游 TSA 64/61/60；每轮 15/15/16
  个单库通过被多库证伪。严格 TSA 有 58 题三轮稳定通过、36 题稳定失败、6 题波动，证明 Exact
  会低估等价 SQL、单库又会高估语义正确，而单次运行无法分离架构与模型方差。
- 影响：当前发布判断以严格 TSA 60–62% 和 36 个稳定残差为事实，不再用 43% Exact 或 76–77%
  单库执行代表产品正确率。下一轮优先把一般 GROUP/HAVING、多阶段聚合、输出实体/可见元组、
  COUNT/SUM/去重主体、布尔作用域和 role-named 关系证据收敛到统一类型化计划，并为模型调用加入
  deadline/取消；本轮不宣称全部残差已修复。三轮固定上游 evaluator 逐题交叉校验均为 100/100。

## ADR-077：结果身份、可见输出、聚合主体和数值域必须形成一个类型化合同

- 日期：2026-08-25
- 状态：已接受；扩展 ADR-071/073/076，不改变访问范围、关系 fail-closed、SQLSecurity、查询行数、
  写预览或显式确认。
- 决定：`RelationalAlgebraContract` 升级到 1.10。实体查询以 `result_grain` 同时声明输出物理所有者、
  稳定身份键、可见列、基数和重复语义；显示名称、描述或类别值不得各自覆盖实体身份。聚合以
  `aggregate_subjects` 明确统计事实行、去重实体或指标值，并要求聚合阶段的分组键与结果身份一致。
  闭合且 FK 路径唯一的关系排名由 Native Relational Planner 在模型前按实体主键编译；不完整或
  相互矛盾的合同继续整句回退或 fail-closed。
- 决定：业务数值域和物理存储类型分开。原生数值列不允许无依据 `CAST` 改变类型/精度；问句明确
  要求最小、最大、平均等数值语义而物理列是 TEXT/VARCHAR 时，合同要求方言化的显式转换和
  `exclude` 无效值策略。无保护 `CAST` 不能执行，因为 SQLite 等方言会把部分脏字符串静默变成
  0；也不能为了匹配 Spider 的字符串型 gold 直接删除数值语义。当前只做验证与重试，不冒充已经
  实现跨方言通用解析器。
- 决定：输出合同可合并显式 `Please also give/list/...` 的跨句追加输出；通用 `id/name` 必须保留
  `of <entity>` 限定，eponymous label 可承担通用 name 角色。SQL 投影校验只读取最外层 SELECT，
  跳过 CTE 和子查询内部 SELECT。Spider/BIRD 反事实重放器升级为 v2，必须先走与生产相同的原生

- 原因：Spider 0374/0530 把名称当 GROUP BY 身份，遇到同名实体会合并；0421 的 museum 输出被
  通用 `ID/Name` 绑到 visitor；0854 的 orchestra name 被绑到 conductor。0095/0169/0975/0986
  则在 TEXT/VARCHAR 业务数值上无保护 `CAST`，多数据库脏值会改变语义。BIRD 0023 明确分两句
  请求 School/Street，旧单句合同只保留 School，局部投影编译反而删除正确地址列；Spider 0225
  的 CTE 还曾把内层 SELECT 误当最终投影。这些都是通用合同/解析边界，不是 gold SQL 风格补丁。
- 影响：固定 DeepSeek 1.8 run1 在当前 1.10 生产路径的零模型重放为 91 接受、8 拒绝、1 澄清、
  错误 0；单库本地改进 0421/0530/0854，普通回归 0。官方 20-schema/695-database 复核完整，
  0421/0854 由失败转为全库通过，8 条本地计划普通回归 0；0374/0530 主键分组正确，但全体并列时
  与未规定次级排序的 gold 任意赢家仍分歧。BIRD 为 55/5，41 个历史正确全部接受，1179 修复改进，
  0023 跨句回归清零，修复回归 0。直接完整安全与功能回归 379/379；这些是固定候选的架构证据，
  不改写 DeepSeek 原始 Exact 43/44/43 或严格 TSA 61/62/60。

## ADR-078：通用单行新增采用 schema 约束的结构化入口

- 日期：2026-08-25
- 状态：已接受；不改变默认只读、访问范围、单语句校验、写入回滚预览、角色授权、
  一次性确认单、审计或执行前复检边界。
- 决定：“能不能写入”“怎么录入数据”等能力型请求，以及已知真实表但缺失新记录值的
  INSERT，在任何模型映射或 SQL 生成之前进入 `StructuredInsertWorkflow`。未指定表时只列出
  当前凭据授权的表；选表后只返回授权字段、SQLite 物理类型、必填/默认/可空元数据
  和通过 `SQLSecurity` 获取的一行原表示例。带业务实体或已明确字段值的自由请求仍保留
  schema 绑定映射，不将一切“新增”简化为全库选表。
- 决定：浏览器提交字段名和 `value/null/omit` 结构，不提交 SQL。后端必须重新按当前 schema
  查找字段，拒绝未授权/重复字段、类型错误、非法 NULL 和缺失的必填值，然后确定性构造一条
  SQLite INSERT。该 SQL 不得直接执行，必须经现有 `WriteSecurity → WritePreviewer` 得到回滚预览
  和绑定当前数据库/凭据范围的一次性确认单，再等待用户显式确认。
- 原因：能力询问和空 INSERT 不是 SQL 生成问题，而是缺少结构化数据采集界面。要求用户记住
  固定口令会把 UI 缺口推给模型；让模型猜表、列或缺失值则会扩大写入风险。用已授权 schema
  和真实示例行向用户索取值，能把意图识别、数据采集和写入授权分成可审计阶段。
- 影响：当前只对已验证本地 SQLite 的单行 INSERT 开放；BLOB、远程只读连接和行级授权凭据
  保守拒绝。直接测试覆盖无模型意图、真实示例、默认/必填/NULL、注入载荷字面值、回滚前
  零落库、确认后执行、行级只读、viewer/operator 边界和审计不记录原始字段值。

## ADR-079：基础沟通使用独立本地路由，不进入数据库执行计划

- 日期：2026-08-25
- 状态：已接受；扩展桌面会话产品面，不恢复 ADR-053/054 已退役的通用会话框架，
  不改变数据库操作计划、访问范围、只读、写预览或显式确认边界。
- 决定：`DBAgent` 在澄清合并、业务语义解析和数据库意图路由前运行独立
  `BasicConversationRouter`。它只接受长度有界且整句匹配的高置信社交意图：问候、感谢/确认、
  告别、身份、能力/用法、状态问候、闲聊邀请、简单情绪、道歉和笑话请求。回答由本地确定性文案

  `DatabaseOperationPlan` 或写确认单。
- 决定：整句匹配是数据库指令优先级的硬边界。“你好，查询…”或“谢谢，删除…”不属于
  基础沟通；`IntentRouter` 可在本地确定性规则前去除这类社交前缀，但模型路由、操作规划和审计仍
  使用用户原问题。短句精确匹配当前澄清候选时，候选值优先，不进入沟通路由。
- 决定：基础沟通可中断已有数据库澄清，但 bridge 必须保留中断前的结构化待澄清状态，
  下一轮仍可直接继续。沟通回答作为 `conversation` 卡片进入会话历史；脱敏审计仍只保存类型/结果等
  白名单元数据，摘要标为“基础沟通”，不保存用户原文。
- 原因：把“你好”“谢谢”送入 RAG/NL2SQL 会把沟通能力误做成数据库查询；恢复通用会话框架
  又会重新引入已删除的产品面和运行时耦合。狭而可证的本地社交通道可以改善日常使用，
  同时不让“更像聊天”成为绕过数据库意图、模型配置或安全边界的理由。
- 影响：桌面欢迎区、快捷问句和回答卡显式表达基础沟通，未配置模型密钥时该通道仍可用。
  它不是开放域知识助手、情感咨询或自由聊天模型；未命中的开放话题仍不获得新的外部能力或数据库
  执行权限。新增回归覆盖零模型回答、礼貌前缀查询/写入、澄清候选优先、HTTP 中断恢复、审计脱敏和前端类型渲染。

## ADR-080：不完整录入由模型识别交互意图，本地 schema 和写入链保持执行权威

- 日期：2026-08-26
- 状态：已接受；取代 ADR-078 中“通用或缺值 INSERT 在任何模型调用前分流”的意图识别顺序，
  保留 ADR-078 的结构化表单、字段类型化、回滚预览、显式确认和全部权限/审计边界。
- 决定：`IntentRouter` 对需要模型判断的数据库请求输出结构化
  `intent / interaction / target_table / confidence / reasoning`。用户表达想写入、录入或新增数据，
  但未提供完整字段和值时，应由模型识别为 `write + guided_insert`；没有唯一目标表时打开授权表
  选择器，模型能从 schema 唯一映射目标时直接打开该表录入表格。含完整值的 INSERT，以及
  UPDATE/DELETE/DDL 等操作使用 `direct_write` 并继续进入原受控写入链。
- 决定：模型不是 schema 或执行权威。`target_table` 只能大小写无关精确匹配当前凭据可见的一个
  真实物理表，否则丢弃并退回授权选表；模型不能指定字段白名单、类型、SQL、确认范围或执行权限。
  `StructuredInsertWorkflow` 只消费已验证的引导录入状态，仍由本地代码读取示例、校验值并构造
  单条 SQLite INSERT，再经过 `WriteSecurity → WritePreviewer → 一次性确认单 → confirm_write`。
- 决定：明确的写入/高风险动作保留本地安全守卫，防止模型把写请求降级为只读；模型服务故障或
  JSON 非法时，只有命中宽泛不完整录入信号的请求可安全兜底到 `guided_insert` 选表入口，不能猜表、
  字段、值或直接落库。路由步骤必须记录 `interaction / target_table / source`，使产品与测试能区分
  模型判断、本地确定性路由、安全守卫和故障兜底。
- 原因：ADR-078 的表单与安全链是正确的，但把“能不能写入”等自然语言在模型前交给窄正则，
  只能证明固定口令可达，不能覆盖“我想往库里加点东西”“帮我录一条客户数据”等真实表达，也无法
  满足产品要求的模型语义识别。把模型限制在交互意图和 schema 候选层，再由本地强校验收口，能扩大
  自然表达覆盖而不扩大写入执行权限。
- 影响：真实 DeepSeek V4 Flash 在 demo SQLite 上把上述三种表达都识别为
  `write/guided_insert/source=model`；前两种打开全局选表，客户表达绑定真实 `customers` 表。
  模型虚构表名回归会退回选表，模型不可用回归只触发安全表单兜底。Python 后端是常驻进程，部署
  本决定必须重启 bridge；只更新磁盘文件不会改变已经加载的路由类。

## ADR-081：自动图表以基础业务表和可解释概览为单位

- 日期：2026-08-26
- 状态：已接受；扩展 ADR-051，不改变数据库＋访问范围缓存键、文件指纹失效、
  生成前后指纹稳定性或只读/authorizer 边界。
- 决定：图表发现必须复用与核心 Schema 一致的 FTS 影子表排除规则，且不把 FTS 虚拟索引
  本身当成独立业务表。同一次冷生成中，表结构、有界采样、范围化行统计和聚合查询复用
  一个只读连接；冷构建放入 worker 线程，不阻塞 aiohttp 事件循环。ADR-051 的单图聚合点上限
  从 200 收紧到 120，缓存 schema 升为 v2。
- 决定：自动图表只产生时间趋势、分类贡献或记录规模三种可说明的形状。响应同时返回
  可见行数、分组数、维度覆盖率、展示点数、截断标志、整体值和基于查询结果的确定性摘要；
  不生成因果解释、预测或模型臆测。前端使用稳定多色调色板，并只为视口附近卡片初始化 ECharts。
- 原因：旧实现对每表反复开连接，还将 `knowledge_fts_data.block` 影子 BLOB 当分组标签，单图
  JSON 约 3.49 MB，超过 2 MB 缓存上限；每次请求因无法落缓存而重做 4.5–5.4 秒的生成。
  这是对象发现与负载边界错误，不是单纯颜色问题。
- 影响：当前复旦库实测强制重建为 357 ms，26 张图完整响应约 25.5 KB，随后缓存读取
  32–41 ms；这是当前本机/文件的实测，不是跨机性能保证。远程数据库图表缓存仍未验证并拒绝开放。

## ADR-082：自定义建表使用受控类型表单，不提供 DDL 直执行旁路

- 日期：2026-08-26
- 状态：已接受；扩展 ADR-003/035/040/078/080，不改变默认只读、写预览、一次性确认单、
  数据库/访问范围绑定、审计完整性或执行前复检。
- 决定：桌面在当前数据库和录入选表弹层提供“新建表”入口。浏览器只提交表名与字段结构；
  `StructuredCreateTableWorkflow` 在后端重新校验 1–64 个字段、安全标识符、
  `INTEGER/REAL/NUMERIC/TEXT/BLOB/BOOLEAN/DATE/DATETIME` 类型白名单、单主键、仅 INTEGER
  主键自增、必填/唯一与受控默认值，然后确定性编译单条 CREATE TABLE。模型不参与 DDL 构造。
- 决定：建表准备端点要求 admin，且只生成 `WriteSecurity → WritePreviewer` 的事务回滚预览和绑定当前
  数据库/范围的确认单；结构变更确认仍按高风险要求 admin。任何表/字段/行或数据库范围受限凭据、
  远程连接都拒绝该 DDL 入口。审计只新增字段数量及目标/确认单指纹，不保存字段名或默认值原文。
- 决定：DDL 执行成功后，bridge 必须清除旧 `DBAgent` schema 快照并重新发现表列表；否则新表虽已落库，
  录入、图表和后续问答仍会使用旧结构。
- 原因：用户需要在不手写 SQL 的情况下定义新表，但直接放开 SQL 编辑或让模型产生 DDL 会绕开类型/约束边界，
  并使高风险结构变更难以审计。受控表单将数据采集、DDL 编译和人工批准分成可验证阶段。
- 影响：真实 bridge 预览约 24 ms，预览前后与拒绝确认后均不存在新表；完整 API 回归还验证 operator
  无法准备/批准 DDL，admin 确认后才创建并刷新 schema。当前不提供外键、表级 CHECK、组合主键、生成列或无表单限制的自由 DDL 编辑。

## ADR-083：模型会话上下文与桌面历史结果使用分离的持久化合同

- 日期：2026-08-26
- 状态：已接受；不改变会话数据库/访问范围绑定、查询行数上限、写确认或审计边界。
- 决定：assistant 消息继续保存最多 3 行、每值 60 字且整体 2000 字的紧凑文本，专门供后续模型
  追问使用。只读 `conversation/schema/query/retrieve/compose/error` 回答可另外保存 UI-only
  `display_payload`：普通表格最多 50 行、最多 64 列，并单独保存真实结果总行数；多分支最多 6 组，
  每组使用相同上限。载荷总计最多 768 KiB，超限时减少快照行而不伪造总行数。
- 决定：`get_history` 永远不返回 display payload，防止模型上下文随 UI 快照扩大；只有通过原会话
  数据库及访问范围校验的 `GET /db/session/{sid}` 才返回富快照。`write_form/write_pending/write_result`
  不保存富载荷，不得在历史中复活确认 ID、确认按钮或自动弹层。旧消息无富快照时继续显示原文本，
  不伪造已经丢失的数据；删除会话同时删除文本和富快照。
- 原因：旧实现为模型追问保存 3 行文本，但桌面切换会话也复用同一文本，导致即时显示十多行的
  “表里有什么”在切换后只剩三行。扩大模型历史会增加上下文、延迟和数据暴露；只保存文本又无法
  恢复用户刚看过的表格，因此必须把两个消费者的数据合同拆开。
- 影响：新产生的只读回答在切换会话或 bridge 重启后按原卡片恢复最多 50 行并显示真实总行数；
  超过 50 行会明确提示当前展示范围。既有旧会话无法从三行文本反推出原结果，需要重新提问一次。

## ADR-084：结果表默认十行，按需展开全部已返回数据

- 日期：2026-08-26
- 状态：已接受；取代 ADR-083 的“富快照最多 50 行”展示口径，不改变模型 3 行上下文、查询
  物化硬上限、会话访问范围、写确认或单消息存储上限。
- 决定：即时单表结果、多分支结果和历史富快照统一默认展示前 10 行；结果超过 10 行时提供低干扰、
  键盘可聚焦并带 `aria-expanded` 的“展开全部 N 行”，展开后显示当前响应或快照中全部行，并可
  “收起到 10 行”。标题始终显示真实结果总行数，不能随收起状态改变。
- 决定：历史快照行上限与只读查询物化硬上限统一为 500，但仍受 768 KiB 单消息载荷上限和 64 列/
  单元格长度边界约束。若极端宽表导致快照缩减，按钮必须写“展开已保存的 N 行 · 结果共 M 行”，
  不得将局部快照称为全部结果；即时响应未触发历史持久化边界时可展开全部已返回行。
- 原因：固定显示 50 行仍会让普通列表过长，而只显示 10 行又不应迫使用户重新查询。渐进展示兼顾
  默认可读性和完整检查；把隐藏行保留在同一回答内，避免展开时重新执行可能已经变化的数据库查询。
- 影响：常见 11–500 行结果可在原卡片内展开/收起；旧三行文本历史仍无法补回，新富快照按当前
  载荷边界恢复。该行为不是分页、导出或解除后端 500 行查询上限。

## ADR-085：分组多指标使用类型化物理计划，不让模型单独决定粒度

- 日期：2026-08-26
- 状态：已接受；扩展 ADR-059/064/066 的关系计划路线，不以 Spider 或两条示例的表面 SQL
  作为进入条件。
- 决定：`RelationalGroupedMetricsPlan 1.0` 只在问句能唯一绑定一个物理维度、2–6 个
  `COUNT/SUM/AVG/MIN/MAX`、类型化字面量过滤和有界排序时编译。全部指标必须属于同一事实表；
  跨表仅接受唯一声明 FK 或用户精确的 `table.column = table.column`，声明 FK 优先作为最终证据。
- 决定：计划保存数据源、维度/分组键、每个聚合主体、关系边、过滤和排序，再由
  SQLite/MySQL/PostgreSQL 方言渲染器重新校验后生成 SQL。多 FK 歧义、多事实扇出、自由聚合表达式、
  未表达条件或少于两个聚合时整句回退，不执行部分语义。
- 原因：旧关系计划只表达单个聚合或把聚合用于排名，对“维度 + 计数 + 金额合计”只能依赖模型。
  这会丢聚合、误选投影，或让旧合同将正确显式 JOIN 误拒绝。
- 影响：已证明形状零模型调用，且在三种方言上共用一个 IR。这不代表通用多阶段聚合、比率、
  相关子查询或多事实指标已确定性支持。

## ADR-086：MySQL/PostgreSQL 仅以真实验证的只读合同对外

- 日期：2026-08-26
- 状态：已接受；不改变 ADR-003/040 的写入预览和显式确认边界。
- 决定：便携运行时精确/哈希锁定 PyMySQL 和 psycopg2-binary。远程 Schema 发现必须包含表、列、
  PK/FK、行数和有界抽样；PostgreSQL 的键元数据不能要求表所有权或写权限，使用只读角色可见的
  `pg_catalog`。方言提示、标识符引用、DECIMAL/日期结果归一与驱动级查询中断必须在共享边界处处理。
- 决定：远程 `DBAgent` 遇到写意图直接返回只读边界错误，不调用 SQLite `connect_rw`、不生成预览或确认单。
  远程表/字段/行级凭据、图表和写入在有等价执行门禁证据前继续禁用。
- 原因：“适配器存在”不能证明可用。真实 MySQL 8.4.9/PostgreSQL 17.11 最小权限测试暴露了 MySQL
  行数读取、PostgreSQL `information_schema` 可见性、DECIMAL 文本化和超时不及时四个实际缺陷。
- 影响：当前可承诺的是上述单版本、单机、整库只读套件通过；云代理、TLS、更旧版本、非 `public` schema、
  组合键语义和网络故障矩阵需分别增加证据。

## ADR-087：原始多语句在模型前整体拒绝，取消是可传播终态

- 日期：2026-08-26
- 状态：已接受；强化 ADR-003/009/044 的执行和审计边界。
- 决定：如果原始用户请求明确要执行并包含两条以上 SQL，必须在基础沟通、意图路由和模型调用前拒绝。
  不能依赖模型只返回安全的第一条 SQL；最终生成 SQL 仍独立经过单语句只读门禁。仅讨论 SQL 关键词的普通文本不得误拒。
- 决定：每个异步 run 绑定独立取消事件。取消 API 必须立即发布 `cancelled/100%`、只记一次终态审计；
  事件向 core 与 LLM 客户端传播，在请求、SSE、重试与退避中协作中止。已返回的迟到结果不得写入会话或覆盖取消终态。
- 原因：只校验模型最终 SQL 会丢失用户原请求中的危险后缀；只设 `cancelRequested` 而不传播事件会让界面在整个模型请求结束后才停止。
- 影响：取消是用户立即可见且对迟到副作用封闭的终态；底层 HTTP 在连接建立前仍受操作系统/请求库能否硬中断的限制，但不再阻塞产品终态。

## ADR-091：远程数据库采用默认只读与显式受控 DML 双通道

- 日期：2026-08-27
- 状态：已接受；取代 ADR-086 的“所有远程写意图直接拒绝”，保留其真实只读合同和证据边界。
- 决定：MySQL/PostgreSQL 连接默认只读。即使用户显式选择受控读写，Schema 与查询仍使用强制只读
  会话；写提案另开非自动提交事务连接，只允许单条 INSERT、带 WHERE 的 UPDATE 和带 WHERE 的 DELETE。
  提案必须先真实执行并回滚得到影响行数/前后值预览，再生成一次性确认单；确认时重新校验并独立提交，
  失败回滚，继续受角色门禁和追加式审计约束。
- 决定：远程 CREATE/ALTER/DROP 继续拒绝。MySQL DDL 可能隐式提交，无法与 SQLite 一样证明预览零副作用；
  远程表/字段/行级凭据也没有等价数据库侧强制门禁。只读连接如果不能证明会话已进入只读状态必须失败，
  不得因为同一账号具备写权限而让查询通道可写。
- 原因：用户需要真实数据库的数据维护能力，但把读连接直接改成可写、或只在 UI 上增加确认，都不能提供
  足够的事务与权限隔离。双通道让功能扩展不削弱默认查询边界。
- 影响：两方言的预览回滚、确认提交、默认拒写和 DDL 提前拒绝已纳入回归；真实 MySQL/PostgreSQL 写服务
  矩阵尚未在本轮环境复现，发布材料必须明确这一证据差距，不能把回归替身描述为真实服务端验证。

## ADR-092：品牌短名不变，公开展示名增加开源品类描述

- 日期：2026-08-27
- 状态：已接受；补充 ADR-090 的公开发现性策略，不改变产品、协议或执行边界。
- 决定：仓库和品牌短名继续使用 `DBQuill`，不把搜索关键词拼入仓库名。README、GitHub About 和对外介绍
  使用 **DBQuill — Open-Source AI Database Agent**，中文使用“DBQuill — 开源 AI 数据库智能体”；副标题明确
  Natural Language to SQL、安全数据库写入和图表。GitHub topics 覆盖 `open-source`、`ai-agent`、
  `database-agent`、`sql-agent`、`nl2sql`、`text-to-sql`、`natural-language-sql` 和已验证数据库/平台。
- 决定：`open-source` 只描述 MIT 许可下公开的项目源码，不暗示连接的模型、用户数据或第三方服务开源；
  `AI Database Agent` 是可发现的产品品类描述，不扩大为开放域通用智能体，也不改变源码优先发布状态。
- 原因：`DBQuill` 提供品牌辨识度，但单独出现时无法让首次访问者和代码搜索立即识别数据库智能体、
  NL2SQL 与安全写入能力。将稳定品牌名和可更新的品类描述分离，可以提高发现性而避免冗长仓库名。
- 影响：只改变公开文案和仓库元数据；现有 URL、tag、发行资产、持久标识、安全合同和运行行为不变。

## ADR-093：界面语言是本地持久化的展示状态，不进入数据库语义

- 日期：2026-08-27
- 状态：已接受；补充 ADR-005 的桌面可读性，不改变自然语言规划、模型配置、数据库访问或审计边界。
- 决定：DBQuill wordmark 旁提供紧凑的“中 / EN”分段选择。界面语言优先使用本机 `localStorage` 中的
  明确选择，首次打开默认英文；页面 `lang`、标题和数字格式同步更新。用户主动切换中文后继续保持中文。
- 决定：中英文目录随源码发布，静态控件、属性、确认提示以及后续动态生成的 UI 节点均在浏览器本地翻译，
  不调用模型、网络翻译或第三方脚本。数据库名、表/字段名、用户问题、模型回答、查询结果和历史业务内容
  保持原文；英文界面不隐式改变发送给模型的提示或数据库操作计划。
- 原因：只在顶栏放一个英文按钮但让二级页面和动态表单继续显示中文，会形成不可用的伪多语言；反过来
  自动翻译业务数据又会破坏证据可追溯性。将界面 chrome 与业务内容分域，才能同时满足可用性和数据忠实性。
- 影响：新增独立 `i18n.js`、持久语言偏好、动态节点观察和中英文响应式布局；安全策略、API、存储 schema、
  发行依赖和模型供应商边界不变。

## ADR-094：大文件上传使用有界流式传输，不在页面构造全量编码副本

- 日期：2026-08-27
- 状态：已接受；修复大 SQLite 上传等待后渲染页崩溃，不改变支持格式和数据源授权边界。
- 决定：桌面文件通过 `multipart/form-data` 直接发送 `File`，显示上传百分比，并在请求体传完后切换为
  “正在检查数据库”状态。bridge 以 1 MiB 分块写入同一会话桶中的隐藏临时文件，累计原始文件大小严格限制
  为 200 MiB；完整接收后才原子改名为正式上传。空文件、超限、连接中断或解析异常必须清理临时文件。
- 决定：上传接口不再接受 Base64 `dataUrl` JSON。文件名仍经过清洗，会话 ID 仍只用于不可逆哈希桶；SQLite
  校验只读系统目录获取业务表名，不执行全表计数或内容扫描。CSV/XLSX 后续转换和数据源注册保持既有边界。
- 决定：bridge 的鉴权状态和 WebSocket 就绪消息公开整数 bridge 协议与命名上传协议。launcher 只有在
  app root、`bridgeProtocol=2` 和 `uploadProtocol=multipart-v1` 全部匹配时才复用已有服务；前端在发送文件
  前再次检查上传协议。multipart 文件名的标准 UTF-8 百分号编码先严格解码，再进入既有叶文件名清洗；
  非法编码保留原始安全文本，不尝试解码数据库内容。
- 原因：旧链路在 WebView 中同时持有原始文件、约 4/3 大小的 Base64 字符串和 JSON 请求体，bridge 又同时
  持有 JSON、Base64 与解码字节。文件越大，峰值内存越接近文件大小的数倍，足以触发渲染页崩溃；它也无法
  给用户提供真实进度。流式落盘使传输内存与文件大小解耦，并把“发送中”和“服务端检查中”分开呈现。
- 影响：内部上传请求合同从 JSON 变为 multipart；公开发行没有承诺该内部接口的稳定性。新增前端零 Base64
  断言、SQLite/CSV multipart 回归、超限清理回归和真实约 51 MiB SQLite 冒烟。该样本本地传输 0.322 秒，
  bridge 工作集观测增量约 0.9 MiB；协议错配和中文文件名另有回归。结果用于回归比较，不代表不同磁盘
  或设备的固定性能承诺。

## ADR-095：实体资料问答使用精确证据计划和可执行会话锚点

- 日期：2026-08-27
- 状态：已接受；补充意图路由、RAG 和会话历史合同，不改变 SQL 只读、关系门禁、权限或写入确认边界。
- 决定：明确人物/主题词优先于通用 n-gram，召回遍历改为“关键词→所有受权表→优先文本列”。
  字段选择按姓名、研究、摘要、描述、证据和状态排序，而非物理前 3 列。一旦明确实体有直接命中，本轮不再向模型提供泛词命中的其他实体。
- 决定：实体状态、已知/未知和证据充分性属于记录证据检索，不因一句包含多个方面就生成 JOIN。
  即使模型路由为 query/compose，本地规则也会将这一明确形状收敛到 retrieve。NL-to-SQL 空结果只在用户原话中存在明确实体且跨表精确命中时回退，
  系统生成的语义字段注释不得被反向解释为用户实体。
- 决定：受限会话历史不只作为模型提示词。对“是什么”“那他的研究方向呢”“证据呢”等短追问，规划器从最近用户轮倒序找到首个非省略主题，将其与当前追问合并后才进入语义、意图和执行层。
- 原因：把历史文本只发给模型，不代表 SQL/RAG 执行器拥有主题。同时表优先、字段物理顺序和泛词优先会在有界证据预算下系统性饿死靠后的精确记录。
- 影响：DeepSeek V4 Flash 真实三轮问答和 430 项完整回归通过。对只能经数字主外键延展的论文/项目，后续仍需关系实体扩展计划；本决定不允许 RAG 猜测跨表关系。

## ADR-096：纠正性指代回溯完整主题，规范档案表优先于文本提及

- 日期：2026-08-27
- 状态：已接受；补充 ADR-095 的会话锚点和实体证据排序。
- 决定：“我的意思是他……”“我指的是她……”“这位老师……”属于依赖上下文的纠正/追问；规划器倒序跳过所有省略或指代轮，以最近的完整命名主题重建执行问题。
- 决定：裸问“某老师的工作”不在“任职/职务”与“研究工作/成果”之间猜测，而是返回两个可继续的澄清选项。明确后的补充会与原始命名主题合并。
- 决定：含显式姓名字段的规范人物/档案表优先召回，其次是同时含姓名和档案信号的表，最后才是审计摘要、声明和其他自由文本提及表。该顺序不改变受权范围和总证据预算。
- 原因：模型在意图推理中正确解析指代，但原始指代句仍直接进入 RAG，会出现“模型知道在问谁，工具却不知道搜谁”。同名在多个摘要表中出现时，纯表名顺序也会在规范人物行前用完证据预算。
- 影响：在正确的 33 表 `fudan_cs_research.db` 上，DeepSeek V4 Flash 对“肖仰华老师的工作”返回含义澄清，纠正为“他担任的工作”后以 `scholars.id=188` 为首条证据，返回教授、博士生导师和实验室主任。433 项完整回归通过。

## ADR-097：通用读路引入有界观察—重规划循环

- 日期：2026-08-27
- 状态：已接受；扩展 ADR-095/096 的实体证据与会话锚点，不改变写入预览、确认、授权和审计边界。
- 决定：初始意图和首个执行结果是可修正假设。对空检索、明确实体的窄投影、计划目标表与实际证据表错位、
  组合图部分失败或用户明确要求继续核验的只读问题，进入 `BoundedReadExplorer`。其每轮只能选择
  `inspect_schema` / `retrieve` / `query` / `finish` / `stop` 之一，且不接收 SQL。
- 决定：模型提出的表必须存在于当前授权 schema；实体必须逐字来自用户原问题。路由模型未给出实体时，本地以问题文本与真实
  身份列值对齐，只把已在数据库出现且完整存在于原问题的值作为执行锚点。后续检索强制携带该锚点，不再依赖“某人的资料”等固定句式。
- 决定：循环默认最多 3 次规划、2 个工具动作、1 次查询、1 次检索和 25 秒真实截止时间；重复动作、实体漂移、未知表、原始 SQL、
  无证据完成均由本地拒绝。截止事件与用户取消合并，能关闭正在进行的模型响应。探索检索只做本地召回，不在工具层再串行一次模型叙述。
- 原因：旧路径可能出现“模型推理知道在问谁，实际检索却搜指代句”、“目标是人物主档案，证据却全来自文本提及表”和“查到 title 就误以为所有职务已覆盖”。
  继续增加句式规则不能解决执行上下文丢失和证据表错位。
- 影响：简单成功查询保持原快路；触发探索时步骤和预算进入结构化 `steps`。该机制是项目专用的只读重规划层，不是开放域自治智能体；写入、修改、删除和 DDL 不进入循环。
